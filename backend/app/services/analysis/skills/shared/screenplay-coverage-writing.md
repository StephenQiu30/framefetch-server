# 剧本审稿报告写法

`screenplay-analysis` 结果由服务端排版为一份审稿报告，顺序是：审稿结论（优先修改、值得保留）→ 故事概览（一句话梗概、故事梗概）→ 结构与节奏 → 人物 → 对白 → 逐场附录 → 阅读说明。本文件说明每个字段在报告中的位置和写法；通用文字规范见《报告写作规范》。

## 报告前半部分：审稿结论

读者最先看到的是 `priority_revisions` 和 `strengths`，它们决定这份报告有没有用。

- `title` 写一句对这份剧本的核心判断，例如“动机清楚，但第二幕的代价没有升级”。原文没有片名时不自拟片名。
- 每条 `priority_revisions[].title` 写成一句判断，12–24 字，读者只看标题就知道问题是什么；不写“结构问题”“人物塑造”这类分类名。
- `priority_revisions[].description` 写 2–4 句：先指出文本中的具体位置和表现，再说明它让读者或观众失去了什么，最后写修改后应达到的结果。可以用“”引用不超过 20 字的原文短句作为依据。
- `strengths[].description` 写清有效的机制、带来的效果和保留它的理由，不写“人物立体”“对白生动”这类评语。

## 故事概览

- `logline` 只写一句话，交代焦点人物、目标、阻力和失败的代价，通常不超过 60 字；不评价，不剧透结局以外的细节。
- `synopsis` 按故事顺序用现在时复述，写 2–4 段，段与段之间用换行分开，每段对应一个主要阶段。梗概只陈述情节，不夹带审稿判断。

## 结构、人物与对白

- `structure.acts[]`、`turning_points[]`：`title` 写出该段或该转折实际发生的事，例如“第一幕：她决定替哥哥顶罪”；`description` 写它改变了什么、依据在哪里。
- `structure.pacing_summary` 写 1–2 段，指出节奏过快、过慢或强度单调的具体区段及原因。
- `characters[]` 的 `goal`、`conflict`、`arc` 各写一到两个完整句子，不写名词短语。静态人物在 `arc` 中说明其稳定立场如何作用于故事。
- `dialogue_findings[]` 与优先修改使用同一写法，指向具体的对话交换。

## 逐场附录

逐场附录供作者对照原文使用，要短而准：

- `purpose`、`conflict`、`turn`、`pacing` 各写一句完整的话；本场没有转变时直接写明“本场没有改变人物处境”，并说明这是否成立。
- `findings` 每条一句，写本场独有的问题或亮点，不重复前面已经展开的跨场问题。
- 指代其他场景时用内容概括，例如“地下室对峙那场”；只有能确定原文顺序时才写“第 3 场”。不要写内部场景 ID。

## 分块与汇总

分块调用中的逐场字段会直接进入最终报告，写法同上。汇总调用写全局字段时，要把分块观察综合成判断，而不是逐块罗列；同一问题在多块出现时合并为一条，并说明它反复出现的范围。
