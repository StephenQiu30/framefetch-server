# 解析引擎重建

本文统一解析引擎的目标、接口、安全边界与真实验收条件。设计 06、07、08、15 分别维护持久意图、Provider、身份入口与工作流的业务职责，解析规则以本文为准；实施状态只在第 8 节维护，过程通过 Git 历史追溯。

## 1. 目标与边界

目标：**冷启动可用**。整套业务服务刚启动，没有热缓存、没有预热，用户粘贴链接后经正式 API 获得完整文件。

- 匿名平台：不依赖任何登录态完成冷启动。
- 登录平台：复用部署者日常 Chrome 中已经登录的必要身份材料，Cookie 与元宝页面账号材料按第 3.4 节分别读取。就绪条件为：Chrome 正在运行且已登录，身份扩展已加载并连接到 cookie-source；页面来源还要求已有对应的已登录顶层页。目标是满足后每次冷启动自动完成下载，当前未验收项见第 8 节。
- 内容范围与身份策略是两个独立维度（见第 4 节）：
  - 默认范围 `public`：只处理能正向证明为公开、免费、非 DRM 的内容。即使带着 Cookie 也不扩张到 private、follow-only、付费或地域受限内容。
  - `personal_full` 范围：只适用于已确认的腾讯视频、优酷个人线路，处理账号可访问的完整非 DRM 单视频，必须保留原始完整时长。
- 不做：解密平台加密媒体、取得内容密钥、转换 DRM 流（视频号加密视频、红果 CENC 流、腾讯/优酷 DRM 格式都属于这一类）。遇到这些情况返回 `content_protected`，并提示使用文件导入入口。
- 单人自用：不建设账号池、准入审批、运营金丝雀或多租户隔离。

## 2. 问题模型：三道关口

三道关口是**诊断维度**，不是一一对应的错误码。同一个信号（例如 LOGIN_REQUIRED、403、空 JSON）在不同平台、不同阶段可能来自不同关口，分类时结合平台、阶段与结构化证据判断（见 3.6 节）。

| 关口 | 平台检查 | 常见信号 | 对应层 |
| --- | --- | --- | --- |
| ① 网络身份 | 出口 IP 信誉与地区 | YouTube `Sign in to confirm you're not a bot`、机房 IP 的 LOGIN_REQUIRED | 出口层 |
| ② 客户端证明 | 是否执行过平台 JS、携带签名/令牌 | 空 JSON、`Fresh cookies needed`、JS 挑战页、PO Token 错误 | 证明层 |
| ③ 账号身份 | 内容是否要求登录或权益 | 明确的登录要求、年龄限制 | 身份层 |

分类使用本次任务实际记录的 egress_class、observed_ip、resolved_layer、client、identity_used 与结构化限制证据，不把路由名、单次机器人墙或元数据成功推广为平台结论。是否解除关口必须由同一出口、客户端与身份上下文中的正式完整文件证明；当前事实与剩余验证只在第 8 节维护。

## 3. 目标架构

```text
链接 → 识别平台 → 平台阶梯（Registry 声明）
                 L1 HTTP 提取（yt-dlp / 薄插件）
                 L2 HTTP + 证明（PO Token、EJS、访客初始化）
                 L3 浏览器解析（真实页面执行 JS，观察响应或调用平台限定的第一方接口）
        运行材料 RunContext（仅在 Runner 内存与私有 tmpfs 中）：出口节点、UA、Referer、Cookie 罐、必要账号材料、浏览器 context
        持久引用 ExecutionContext（无秘密，写入业务库）：见 3.7 节
        成功 → 作品身份 + 语义下载规格 → 下载前核对 ExecutionContext → 同层重新取直链 → 下载 → 校验 → 发布
```

### 3.1 出口层

- 每个平台声明固定出口 `egress_route`：`cn_residential` 或 `global_residential`。squid 按路由把流量转给 Clash 的对应上游，Runner 只认路由名。
- 路由名不代表实际住宅出口：配置住宅上游时记录 `egress_class=residential`；未配置境外住宅上游时复用现有境外节点并标记 `datacenter`，国内直连未声明固定住宅上游时标记 `unknown`。当前部署复用已有宿主出口，YouTube 按 Registry 的 prefer 身份与 PO Token 链执行；能否通过以同上下文中的完整交付判断，不以出口类别代替验收。
- 同一任务的解析与下载必须走同一路由、同一出口节点。路由配置修订（`egress_revision`）和观测到的出口 IP（缓存 10 分钟）写入 ExecutionContext 与诊断。
- 在同一个被封锁的出口下切换层级，不算解决了关口 ①；诊断里要如实记录出口类别。

### 3.2 证明层

- 签名与令牌只来自两类组件：执行平台自身 JS 的组件（浏览器、BotGuard 运行时），或上游维护中的官方求解器（例如 yt-dlp TikTok 提取器自带的挑战求解）。仓库内不自己实现逆向签名算法。
- YouTube：
  - 成对升级 yt-dlp、EJS、JS 运行时、bgutil 服务端与插件到当前版本，删除发行身份校验。
  - L2 客户端链按顺序尝试，例如 `mweb`+bgutil PO → `tv` → yt-dlp 默认；每一步记录实际使用的 `client`。
  - L3 使用 [yt-dlp-getpot-wpc](https://github.com/coletdjnz/yt-dlp-getpot-wpc)。它是 PO Token 提供者，不是页面解析器：由它自己启动浏览器（上游用 nodriver，`headless=False`，容器内需要 Xvfb），取得令牌后仍由 yt-dlp 完成解析和下载。它和 3.3 节的 Playwright 预言机相互独立，使用同一出口路由；令牌与视频 ID、出口的绑定规则以上游说明为准。
  - 某个客户端只返回 DRM 或 SABR 格式时，只说明该客户端不可用，继续尝试链上的其他客户端。所有声明客户端都只有 DRM 格式时，才判定为 `content_protected`。
- 快手、微博的 L2 准备步骤：按平台声明请求首页或 `passport` 访客接口，取得访客 Cookie 后再调用 yt-dlp。
- 抖音、小红书：访客初始化和签名由 L3 浏览器完成。

### 3.3 浏览器预言机（L3）

- 基于现有 `browser_runtime`（Playwright + Chromium），懒启动。
- **匿名 context**：每个平台一个常驻 persistent context（`browser_profiles` 卷），**永远不注入账号材料**，空闲 10 分钟关闭。
- **登录 context**：需要身份的任务使用独立的临时 context，在私有 tmpfs 中创建，绑定任务、站点和登录材料摘要。任务成功、失败或取消都要销毁，匿名任务不能复用。
- 同一平台的匿名 context 同一时刻只由一个任务占用；并发请求排队，排队时间计入解析时限。
- 统一流程：
  1. 打开平台首页，完成访客初始化。
  2. 打开作品页，按平台声明的 URL 模式拦截页面自己发出的接口响应，例如抖音 `aweme/detail`、小红书 `feed` 或 `__INITIAL_STATE__`。
  3. 由平台薄解析函数转成统一的 `ResolvedMedia`。
- 视频号使用第 8.5 节的专属流程：分享页／匿名 feed → 无媒体时用已登录元宝页面的原生 JS 生成认证与动态签名 → 固定元宝解析接口 → 可播放引用 → 微信官方 feed → 媒体。它可以主动调用已声明的精确第一方接口，不限定为等待页面自行发出响应；请求目标、方法、请求体和响应来源由平台实现固定，不开放任意 URL、脚本或接口代理。仅解析本次用户提交的分享作品，签名不在仓库内逆向实现。
- 下载交接：把 context 的 Cookie、UA、Referer 放进 RunContext，由 HTTP/yt-dlp 下载。如果证明媒体直链绑定在浏览器上，就在同一 context 内下载到 workspace，文件保存完成后才关闭 context。

### 3.4 身份层

唯一来源是用户普通 Chrome Profile 中的扩展。Cookie 身份通过 `chrome.cookies` API 提供；视频号另有第 8.5 节限定的元宝页面账号材料类型，两者不得混装。不读取 Profile 文件，不访问钥匙串，不需要完全磁盘访问，也不解密 Cookie 或媒体。

组成：
- **扩展 `framefetch-identity`**（MV3）：
  - 申请 `cookies`、`alarms` 和 `scripting` 权限；`host_permissions` 只包含 Registry 中需要身份的平台所声明的 Cookie 域、明确声明的页面身份 origin 对应模式，加上 `ws://127.0.0.1:<端口>/`。当前页面来源仅允许 `https://yuanbao.tencent.com/*`，不用广泛 `tabs` 权限。
  - manifest 带固定的 `key`，扩展 ID 因此稳定；`minimum_chrome_version` 为 120。
  - 事件监听器在 service worker 顶层同步注册；每次 worker 启动都检查并补建 alarm；连接初始化必须幂等。
  - 仅对已有非无痕元宝顶层标签页运行固定 ISOLATED 只读函数，按第 8.5 节读取必要 Storage 字段；不提供任意脚本或取值接口，不读取 DOM、整份 localStorage 或浏览历史，不创建／导航用户标签页。
- **宿主 `cookie-source`**（LaunchAgent，普通进程，不需要任何系统特权）：
  - 只监听 `127.0.0.1`，提供三个入口：
    - 面向扩展的 WebSocket `/extension`；
    - 面向 Runner 的 `POST /cookies`（传递方式见下文）。
    - 面向 Runner 的固定 `POST /yuanbao-account`，只接受视频号的声明来源，复用 Cookie 入口的认证与请求约束。
  - 不保存账号材料，不维护材料库；每次请求都实时向扩展索取。

扩展连接：
- 扩展的 service worker 主动连接 `ws://127.0.0.1:<端口>/extension`。连接建立后，双方用配对密钥做**双向**挑战应答认证：
  - 双方各自发送一个随机 nonce。
  - 双方用 `HMAC(配对密钥, 角色标签 ‖ 对方 nonce ‖ 己方 nonce)` 回应，角色标签区分 `server` 和 `extension`。
  - 原始密钥不在连接中传输。
  - 扩展只有在验证服务端应答成功之后，才处理声明来源的身份请求；cookie-source 同时校验 Origin（`chrome-extension://<固定 ID>`）与扩展的应答。
  - 任何一方认证失败或认证超时（5 秒），连接关闭。这能防止 cookie-source 停止期间，本机其他进程抢占端口冒充服务端骗取 Cookie。
- 只绑定一个配对的普通 Profile：认证成功的连接只能有一条，第二个连接不能替换已有身份。扩展只读取它所在 Profile 中声明来源的身份材料。
- 范围限制：
  - 只支持非分区 Cookie（CHIPS 分区 Cookie 不读取）。如果某个平台的正例确实依赖分区 Cookie，再作为该平台上线时的阻塞单独处理。
  - 扩展按 Registry 的域规则过滤 `getAll({domain})` 的结果，包括子域。
  - cookie-source 限制连接数、消息大小和并发请求，每个请求用 `request_id` 关联响应。
- 保活与重连：
  - 连接期间每 20 秒互发心跳。WebSocket 有消息往来时，Chrome 会延长 service worker 的生命周期（Chrome 116 及以上）。
  - 断开后立即重连，失败时指数退避，上限 30 秒。
  - 用 `chrome.alarms` 每 30 秒检查一次连接，并在 `runtime.onStartup` 与 `runtime.onInstalled` 时触发连接，覆盖 service worker 被回收和 Chrome 重启的情况。
- 请求流程：
  1. Runner 调用 `POST /cookies {site, task_id, deadline}`。
  2. cookie-source 经 WebSocket 向扩展发送 `{request_id, domains}`，`domains` 由服务端根据 Registry 中该 site 的声明确定，扩展不接受任意域。
  3. 扩展调用 `chrome.cookies.getAll({domain})`，只返回这些域的 Cookie。
  4. cookie-source 过滤掉过期项，计算材料摘要（基于必要 Cookie 的稳定 HMAC），再返回给 Runner。
  单次请求限时 5 秒。
- 扩展未连接、超时或返回为空时，结果为 `identity_unavailable`，子因分别是 `extension_disconnected`、`extension_timeout`、`credential_missing`。不尝试其他读取方式。
- 页面账号请求使用独立 `yuanbao_account` 消息，携带固定 site、request_id 和操作 UTC 截止时间，不传 Cookie 域或任意来源；扩展读取上限为操作剩余时间与五秒的较小值，截止后不再启动下一次 Chrome 调用。只返回固定 origin 和必要账号字段，服务端生成稳定 HMAC 摘要与本次操作使用截止时间。Cookie 入口不得读取页面账号材料，细节见第 8.5 节。

安装（一次性部署步骤，2026-10-01 用户决定从项目目录加载扩展）：
- 扩展直接从主仓库目录 `video-server/browser-extension/` 加载；代码更新后在扩展页点“重新加载”即可生效，扩展版本与后端代码一致。
- `cookie-source install` 完成以下事情：
  - 生成扩展配对密钥（与 Runner 的 Bearer 令牌分开，互不复用）；
  - 把密钥与端口写入 `browser-extension/config.local.json`（权限 0600，属当前用户）。该文件写入 `.gitignore`，不得列入 `web_accessible_resources`，不得进入日志或发行包。`install` 和测试检查该文件未被 git 跟踪；
  - 依据 Registry 生成 manifest 的 `host_permissions`，作为构建产物写入（同样被 gitignore），源码中只保留模板；
  - 安装 LaunchAgent。
- 信任边界：配置文件能挡住网页和其他用户，但挡不住同一用户下能读写项目目录的恶意进程，这一点在 README 中写明。
- 部署者在 Chrome 的 `chrome://extensions` 中开启开发者模式，点“加载已解压的扩展程序”，选择 `video-server/browser-extension/`。之后无需再做任何操作。
- 升级时，`git pull` 之后运行一次 `install` 更新生成的文件，再在扩展页点一次“重新加载”。`cookie-source check` 会报告扩展的连接状态与版本。
- 不要从 git worktree 加载扩展：扩展固定从主工作区目录加载。

就绪条件与冷启动：Chrome 正在运行，扩展已加载且已连接，目标平台在 Chrome 中已登录。服务重启后，扩展会自动重连；Chrome 未运行时，登录平台的结果为 `identity_unavailable`（`extension_disconnected`），匿名平台不受影响。

传递：

- `cookie-source` 只监听宿主 `127.0.0.1` 上的固定端口，容器经 Docker Desktop 的 `host.docker.internal` 与固定代理入口访问，不设置身份中继。
- 只有 Runner 持有访问令牌（Bearer，来自类型化配置），其他容器没有这个令牌。未认证的请求返回 401。
- 网络通路：Runner 所在网络没有直接出网能力（R4 实测 `Network is unreachable`）。对 cookie-source 的请求经现有 egress-proxy 转发：
  - squid 精确放行 `host.docker.internal` 与 cookie-source 端口的组合。这条例外放在现有私网 / `.internal` 拒绝规则之前，并且只匹配这一个组合；其他私网、IP 字面量和宿主上的其他端口仍然拒绝。
  - 宿主请求由 squid 直连（`always_direct`），不得经过 Clash 或住宅上游，以免令牌和 Cookie 被转发出去。
  - Runner 的身份客户端显式指定代理，并禁止跟随重定向。
  - egress-proxy 因此成为新增的敏感传输信任组件：明文 HTTP 下，它能看到令牌和 Cookie。squid 不记录这条路由的请求头和响应体。
- 请求 `POST /cookies`，参数为 `{site, task_id, deadline}`。服务端只返回该平台声明域中未过期的 Cookie，外加材料摘要（基于必要 Cookie 的稳定 HMAC）。不做密封、不维护会话代账本、不发租约。
- Runner 把 Cookie 写进本次操作的私有 tmpfs 文件。操作结束（包括异常和取消）时删除；Runner 启动时清空整个 tmpfs 目录，覆盖异常退出的情况。
- Cookie 不进入业务数据库、队列、Temporal、API 响应、日志或 AI。

使用时机由平台声明的 `identity` 决定：

| identity | 行为 |
| --- | --- |
| `required` | 每次进入阶梯前取得必要材料，只在声明的域／origin 对应身份阶段使用；身份不可用则终止为 `identity_unavailable` |
| `prefer` | 扩展已连接、且读到该平台的必要 Cookie 时，每次都注入；身份不可用时按匿名继续，不因此失败（记录 `identity_used=false` 与子因） |
| `optional` | 出现登录要求的证据后，在同一任务内注入并重试一次 |
| `none` | 永不注入；遇到登录要求直接终止为 `login_required` |

当前部署直接复用普通 Chrome 中已登录的会话与已有宿主出口。YouTube 为 prefer 身份策略，实际线路与客户端由 ExecutionContext 记录；完整交付证据见第 8 节。

身份不可用（扩展未连接、未登录、读取超时）时：`required` 平台终止为 `identity_unavailable`；`prefer` 平台按匿名继续，ExecutionContext 记录 `identity_used=false`、`identity_digest=null`，子因写入失败记录的结构化 `evidence`。ExecutionContext 保持 12 个字段不变。两种情况都不反复重试。

### 3.5 阶梯执行规则

- Registry 为每个平台声明：`ladder`（有序层级）、`egress_route`、`identity`、`content_scope`、L3 拦截规则，以及 L2 准备步骤。
- 失败转移表：

| 失败类别 | 下一步 | 次数上限（作用域） |
| --- | --- | --- |
| `network_blocked` | 下一层（诊断标注出口类别） | 每层 1 次 |
| `challenge` | 下一层 | 每层 1 次 |
| `extractor_broken` | 下一层 | 每层 1 次 |
| `format_unavailable` | 下一层；已是最后一层则终止 | 每层 1 次 |
| `login_required` | 已注入身份或 `none`：终止；`prefer` 未拿到身份：终止（无可用身份） | — |
| `identity_unavailable` | `required`：终止；`prefer`（解析开始时读取失败）：匿名继续；下载前核对时，解析时用了身份而下载时拿不到：`context_changed` | 每个任务读取 1 次 |
| `rate_limited` | 遵守 `Retry-After`，等待时间在剩余预算内就同层重试一次，否则终止 | 每个任务 1 次 |
| `transient` | 同层重试 | 每层 1 次 |
| `runtime_unavailable` | 同层重试；再次失败就终止，不切换层掩盖本机故障 | 每个任务 1 次 |
| `content_unavailable`、`content_protected`、`invalid_input` | 终止 | — |

- 预算：
  - 解析时限为每个 generation 120 秒，截止时间持久化在意图上。所有层、重试、排队和身份读取共享剩余时间。自动恢复或 Worker 重启不重置截止时间，只有用户显式 refresh 才开启新的 generation。
  - 下载、校验和发布另设有限时限（沿用现有下载预算）。下载时需要重新解析取直链的，计入下载时限，不开启新的解析预算。
- 超时或取消时，终止整个子进程组和浏览器 context，确认清理完成后才写终态。
- 解析成功后，记录作品身份、语义下载规格和 ExecutionContext。
- 下载开工前核对 ExecutionContext。未变化就同层重新取直链；取到后再次核对实际使用的客户端、作品身份与语义规格，任何一项不符都按 `context_changed` 处理。发生变化（出口节点或修订、客户端、引擎修订、登录材料摘要）就标记 `context_changed`，要求重新解析并重新确认规格，不静默更换。

### 3.6 失败分类

类别：`network_blocked`、`challenge`、`login_required`、`identity_unavailable`、`rate_limited`、`content_unavailable`、`content_protected`、`extractor_broken`、`format_unavailable`、`transient`、`runtime_unavailable`、`invalid_input`、`context_changed`。

- 每个失败记录 `layer`、`stage`（resolve / download / validate / publish）、`gate`（① / ② / ③ / none）、`evidence`（结构化子因，不含原始 stderr）和一句摘要。
- 分类优先级：先判断明确的内容限制或删除，再依次判断限流、登录、挑战、网络、结构与格式；只有模糊提示时归为 `extractor_broken` 并保留证据。
- 同一任务的多层失败都保留下来，最终摘要指出停止原因。

当前调用与安全约束：

- 出口传递：`RunContext.egress.proxy_url` 是 Runner 内媒体出站的唯一代理来源，yt-dlp、媒体 HTTP / FFmpeg、`browser_runtime`、缩略图请求全部从它读取。身份服务经第 3.4 节的固定宿主代理入口访问。
- 实际上下文：`run_ladder` 返回的 `Resolution.execution_context` 是解析结果的唯一来源，`service.py` 把它原样持久化。下载开工前，用持久化的上下文与重新解析得到的上下文做 3.5 节核对。
- 阶梯分派：`ladder.py` 按 `profile.ladder` 通过层表 `{L1: HttpLayer, L2: PreparedLayer, L3: BrowserLayer}` 依次执行，使用 3.5 节的完整转移表、共享截止时间与预算。
- Cookie 输入：yt-dlp 命令接受 `RunContext.cookie_file`，只允许 Runner 的 `/tmp/framefetch-identity/<operation>/<file>` 私有 tmpfs 路径（目录 0700、文件 0600、当前用户所有、无符号链接），其他路径一律拒绝。
- 浏览器交接：`BrowserHandle` 提供 `cookies()`、`user_agent`、`async download(url, dest)` 与 `async close()`。`ResolvedMedia.handoff == "browser"` 时，下载走 `BrowserHandle.download`，文件保存完成后才关闭。`RunContext.with_material(...)` 返回带新材料的副本；层通过 `ResolvedMedia.run_context` 返回，阶梯把最终材料放入 `Resolution.run_context`，由 service 持有到交接结束并释放，任何材料均不序列化。下载核对用的持久上下文通过 `ResolutionSource.expected_context` 传入。
- 引擎修订：`version.py` 提供 `engine_revision()`，按 yt-dlp、插件、EJS、bgutil、WPC、浏览器版本组合计算。
- 公开只读上下文：`InspectionResponse` 与 `DownloadResponse` 提供只读的 `execution_context`（3.7 节的 12 个字段，不含秘密），OpenAPI 与 Web / App 客户端保持一致，矩阵从正式响应读取。

## 7. 验收：冷启动矩阵

- 脚本 `backend/scripts/coldstart_matrix.py` 读取 `backend/scripts/fixtures/coldstart_cases.json`，有两种模式：
  - 阶段模式 `--platforms a,b`：只运行指定平台，并严格检查这些平台各自至少有两条正例；用于 R2–R4 的阶段验收。
  - 全量模式 `--all`：平台集合必须等于 Registry 的全部平台，缺少平台就报错；R5、R6 与最终验收只用这个模式。未覆盖的平台不能记为通过。
- 每条样本声明：平台、URL、预期作品 ID、独立来源的完整时长（不能取自被测流本身）、预期的最低规格、`content_scope`，以及类型（正例 / 受保护负例）。
- 每个平台至少两条相互独立的正例（不同作品）。
- 冷启动范围：
  - 重启 api、worker、session-runner 与 cookie-source（阶段模式只重启本阶段已实现的组件）。
  - 清空 Runner 的临时目录与 yt-dlp 缓存。
  - 使用独立的验收浏览器卷，不动日常卷。
  - 共享基础服务（PostgreSQL、RabbitMQ、Temporal、MinIO）保持运行。
- 每条样本经正式链路执行：API 创建意图 → Temporal 解析 → 确认规格 → RabbitMQ 下载 → Artifact 发布 → 取回文件 → ffprobe → 完整解码。随后按样本声明核对作品 ID、完整时长（容差沿用 `verification.py`）与规格，记录实际时长、大小和 SHA-256。
- 输出 Markdown 与 JSON：平台、样本、结果（通过 / 失败 / 阻塞 / 受保护负例）、成功层级与客户端、出口类别与观测 IP、是否使用身份、耗时、失败类别与证据。结果存到 `artifacts/coldstart/`，不提交仓库。

### 8.6 视频号与 Dailymotion 接入调研及实施顺序

本节规定视频号与 Dailymotion 的接入职责和完成标准。Dailymotion 已接通匿名 L1 与正式 Web 入口，当前清单网络拒绝仍阻塞完整文件交付；视频号已完成身份接线，专属解析器仍缺失。能力声明与真实验收分别记录，不能由实现登记推定下载成功。

| 平台 | 当前失败位置 | 最小处理路径 | 首阶段范围 |

**视频号的具体接线缺口。** 历史“元宝 Cookie”实际把网页 Storage 中的账号字段、页面原生动态头混装为合成 Cookie。`398bf017` 删除元宝固定解析 fallback 与后续官方 feed 交接，是可以从 Git 确认的功能回归；恢复协议职责，不恢复旧 Broker、持久账号 Profile 或合成材料载体。当前 `YuanbaoAccountMaterial`、固定宿主接口、扩展读取函数和 Runtime 私有 tmpfs context 已完成离线接线；通用 `BrowserLayer` 明确拒绝该账号类型，`PageResponses` 的通用主机推导也不适用于元宝／微信双来源。需要在现有 L3 入口增加视频号专属 `resolve(source, ctx)` 分派，按精确来源处理固定请求和响应，复用共享截止时间、出口、取消及浏览器所有权，而不是仅向通用 `PARSERS` 填一个名字。

本轮只读取生成 manifest 的权限字段：当前生成的 version 1.0.0 仍为 `cookies/alarms`，没有 `scripting` 或元宝 origin 授权；这不是 Chrome 实际加载状态的证明，新旧模板均为 1.0.0，不能只靠版本号辨别。源码具备这些能力不等于普通 Chrome 已加载；正式接入须生成当前扩展、重载并完成实际权限／认证验证，保留既有配对和 Runner 凭据。两个 Storage 字段能否恢复今日账号、历史页面原生方法是否仍存在和正确绑定请求，均需当前真实证据，不能根据旧函数名编造调用。最终适配必须绑定分享作品、元宝解析响应与官方 feed 的同一作品／完整时长，媒体规格不能照搬旧 policy 的硬编码 AAC；验证清楚后转为现有 `ResolvedMedia`，只有确实依赖浏览器时才使用内存 `BrowserHandle`。

**Dailymotion 最小实施范围。** 当前 yt-dlp 固定于 `51bab8a0116f4d8004c315706d809782607d5847`，原生 Dailymotion 提取器已包含匿名 client-token、第一方元数据和 HLS 路径。它提供实现基础，不证明今日匿名接口一定成功。上轮正式入口拒绝测试使用的 `x2iuewm` 在上游测试中已标注视频删除，不能迁为上线正例。实施分为以下职责：

1. 在 `provider_types.py`、`provider_catalog_public.py`、`provider_normalizers.py` 增加平台 key／Profile 标识和精确单视频 URL 规则，再从拒绝集合移除对应域；初始支持规范长链与 `dai.ly` 短链，embed／player 等别名只有规范化、作品绑定和测试齐全后再纳入。上游会把带 `playlist` 参数的链接改为集合解析，现有 capability 声明本身不是集合执行闸门；有明确视频 ID 的长链须去掉集合／跟踪上下文，插件仍拒绝意外 entries／直播结果。拒绝频道、搜索、仅播放列表与直播入口，不借 Generic 放开所有未知站点。
2. 声明 `L1/global/identity=none/content_scope=public`，首阶段只声明单视频能力，Cookie 域为空。`prefer` 的现有语义是先尝试读取身份再匿名降级，不能把它描述为匿名优先。无需为公开正例新增扩展权限、账户配置、浏览器平台解析器或基础服务。
3. 复用 pinned `DailymotionIE`，增加站点专属薄可信插件，保留原始响应的公开性、限制和完整时长证据。原生提取的常规结果只保留展示信息和格式，不能把缺少 private／试看字段当作公开完整。优先核实第一方作品元数据的 `id/private/password_protected/published/status/duration`，地域信息按实际接口核实；缺失、结构变化或歧义明确失败，不根据可播放 URL 自行填 `availability=public`。旧公开元数据 API 的今日匿名可读性仍是 POC 前提，不能用企业 OAuth 的 API v2 要求或文档字段推定实际响应。
4. MP4／HLS 候选接入现有下载前重解析与文件核对。HLS 在处理主清单及实际选择的 variant 前校验保护标签、有限 VOD 和完整覆盖，拒绝加密 Key，不允许原生下载器自动取 Key 或解密；清单请求继续受大小、时限和出口限制。固定提取器没有独立 MPD 分支，首阶段不宣传 DASH；增加该能力时先实现 MPD／`ContentProtection` 判断并取得真实 clear 正例。只给 `has_drm=false` 或先成功播放不能替代这些检查。
5. 在当前 `schema.sql` 的平台目录幂等种子中加入 Dailymotion 展示行，既有数据库另受控登记可见目录记录；下载来源目录补展示／统计分类，不新增 DDL、表、任务路由、调度器或秘密字段。Web 的平台状态与能力继续从 Registry／数据库派生，App 的平台 key 也是字符串，使用现有能力类型时不需改变公开 OpenAPI 字段或生成客户端。同步 Registry／目录／Generic 防绕过回归，在唯一 `coldstart_cases.json` 增加两条独立正例并更新当前硬编码 24 个 Profile 的矩阵契约；新增平台后全集为 25，专项与完整 `--all` 的集合要求不能混淆。Profile 的 `unknown` 是可执行接入声明，现有 `download_supported` 表示入口能力，不表示真实验收通过；不增加虚构的 verified 开关。实现接通后经正式 API POC，真实结果单独维护在第 8 节，不能在未测试时宣称平台已通过。

**身份扩展与后续平台。** Chrome Cookie 读取需要 `cookies` 和对应 host 权限，当前域列表由 Registry 的 required／prefer Cookie Profile 派生，宿主另有必要账号字段规则。因此不能把“yt-dlp 有提取器”解释为插件可以读取任意域。Dailymotion 公开 POC 不改扩展；若之后真实样本证明必要身份，应独立核实来源域和必要账号字段、声明身份策略、更新生成 manifest 并实际重载，再验证材料 HMAC、私有 tmpfs 和重解析一致性，不把上游访客 token 当作普通 Chrome 登录凭据。类似平台继续复用 Registry＋薄适配＋统一交付，避免为每站复制任务系统或申请全部网站 Cookie 权限。

**官方 API 的适用范围。** Dailymotion 官方 Download API 面向自有内容，要求 Pro Enterprise 与 Stream URL 功能、具备生成地址权限的私有 API Key 及 `video.read`；地址有时限。它是具备上述条件时的官方导出选项，不是普通公开链接接入的必备依赖，也不能由普通网页登录 Cookie 替代。本次不增加企业 API 凭据接口。参考 [固定 yt-dlp 提取器](https://github.com/yt-dlp/yt-dlp/blob/51bab8a0116f4d8004c315706d809782607d5847/yt_dlp/extractor/dailymotion.py)、[Dailymotion Download API](https://developers.dailymotion.com/docs/generate-download-urls)、[作品字段](https://developers.dailymotion.com/v0/reference/video-fields)、[DRM 文档](https://developers.dailymotion.com/docs/implement-drm-using-dailymotion-player)和[Chrome Cookie 权限](https://developer.chrome.com/docs/extensions/reference/api/cookies)。

**顺序及完成标准。** Dailymotion 完成公共匿名 POC，核实第一方访问证据和清单边界后接通正式 Web 下载；视频号先验证账号恢复、原生方法和解析响应，再完成专属 L3 与统一下载交接。两者各需两部当前存在、用户有权获取、独立完整时长和公开免费 clear 证据齐全的作品，经正式入口解析、选择规格、创建任务、发布 Artifact 并实际保存文件，核对 SHA-256／ffprobe／严格全片解码；同时覆盖私密／保护／缺证据、跨作品、过期票据、取消和服务重启。Dailymotion 第一批至少包含长链与短链，不能复用已删除旧样本；视频号继续满足第 8.4／8.5 节门槛。复用现有 Temporal 与基础服务，专项通过仍不等于完整 `--all` 通过。

**2026-10-02 实现状态。** Dailymotion 已登记独立匿名 L1 Profile、精确长短链、来源目录与现有数据库展示行；其余 Dailymotion 子域仍在 Generic 前拒绝。薄插件先核实公开作品 API，再绑定原生 GraphQL／player 的同一作品、原始时长及显式保护字段。HLS master 与实际 variant 均在原生解析前检查保护标签，保存经校验的清单；重定向后的相对 URI 使用最终响应地址。本阶段 HLS 仅支持完整 MPEG-TS VOD，拒绝 Key／Session Key 的异常分隔、MAP、BYTERANGE、LL-HLS、I-frame、GAP／SKIP；固定 `--abort-on-unavailable-fragments`，不能跳过缺片后报完整。既有 MP4／HLS 统一下载、重解析与文件校验不变，不声明 DASH。两个当前匿名官方 API 样本 `x5kesuj`／`x93blhi` 的独立时长为 187／217 秒；公开发布、无密码、无限地域与 player 保护标志已核实，裸清单请求返回 403，夹具 clear 可交付资格仍为 `unverified`；本轮正式原生提取器也收到清单 HTTP403，未通过完整文件验收，最终结果见第 8.7 节。新增平台后 Registry／唯一矩阵样本集合为 25，集合契约通过不代表全平台验收。
