# 解析中心与持久意图

本页描述当前实现。解析已迁入 Temporal，保留持久业务意图与 API 幂等语义，执行与取消由单 Activity Workflow 负责；不得同时保留两套任务执行所有者。工作流分工见[设计 15](15-工作流与平台下载目标.md)，解析引擎目标与实施顺序见[设计 17](17-解析引擎重建.md)。

解析不在 HTTP 内同步等待，而是以持久的 `download_intent` 为唯一入口：

- **接单**：输入规范化（`public_input` 从分享文案提取恰好一个 HTTP(S) URL，多个 URL 拒绝）、加密存储、owner 配额与 Outbox 在同一事务提交，返回 `202`。`(owner, idempotency_key)` 唯一；重放只返回原意图，不重置 120 秒截止。
- **状态机**：`queued → resolving → ready → handed_off`；取消或超期先进入 `cancelling`，确认 Runner 清理后才进入终态 `cancelled / expired`；其他失败为 `failed`。同一意图的 generation 与当前状态阻止取消后及刷新前的迟到结果写入；保留业务 generation/fence、持久截止时间与取消确认。
- **执行**：worker 进程内的 `ff-inspect` Temporal 队列保留两个解析 Activity 槽；`InspectionWorkflow` 只调用一个 resolve Activity 并传递取消。工作流 ID 为意图 ID 加 generation，Outbox 确认丢失时核对既有绑定。解析复用 Runner 活跃任务与取消接口，清理确认前保持 `cancelling`；断连触发清理，但不能替代确认。基础设施中断可在同一原截止时间内重跑，当前版本拒绝旧执行迟到结果。
- **结果**：inspection、formats 与 `ready` 在同一事务提交。格式推荐顺序是后端规则（优先保留音轨，再按分辨率、容器、编码、帧率稳定排序），投影与探针一致。仅 `access_decision=downloadable` 可确认下载；确认后由既有 `POST /api/downloads` 交接，同一 inspection 唯一交接。
- **过期与刷新**：inspection 过期后 `refresh` 保留原意图并递增 generation，重解析必须核对平台内容标识与媒体类别，格式变化须用户重新确认，不自动下载；不复用失效直链。
- **来源发现**：微信公众号文章先做多候选发现，用户显式选择后再解析。
- **恢复**：客户端响应丢失时以同一幂等键只读查询（不重发 POST）；账号绑定的历史列表（游标分页，单页最多 50）用于跨设备找回，不返回原始输入或幂等键。
- **个人处理记录**：`GET /api/download-intents/history/records` 对解析意图、视频 AI、剧本基础解析、剧本 AI 做 owner 范围联合查询（排序 `created_at DESC, id DESC, record_type DESC`，过滤先于 LIMIT，无 COUNT），不新增万能任务表；来源与结果可用性分别标注 `available/unavailable/unknown/not_applicable`；详情与写操作重新校验权限。
- **管理员操作日志**：`operation_logs` 记录写请求生命周期（路由执行前 started、完成后一次结果写入）与由 SQL 触发器在业务事务中写入的任务状态事件；不持有用户外键、不记录完整 payload；入口 `/admin/operation-logs`。个人记录入口 `/history/activity`。

解析结果、意图、下载 Job 与制品元数据的上下文、失败分类和下载前核对统一遵循[设计 17 第 3.5–3.7 节](17-解析引擎重建.md#35-阶梯执行规则)。
