## 1. 审查范围与结论

以本地 `6fb8f10d` 及本轮开始时的未提交改动为审查范围，覆盖 Web 身份恢复、Provider 授权事务、浏览器桥、启动策略、Compose、相关测试，以及独立 App 的路由和公开页面改动。另检查既有下载准入、工作池、消息确认、Outbox 和任务租约。按 review-agent 方法区分新增回归与原有问题，不以静态阅读声称逐行穷尽全部仓库，也不将旧 040 的发现原样重复。

040 中的控制目录挂载、跨 UID 请求原子发布、Redis CAS 终态、结果落库后确认、管理员权限、关闭窗口 generation 等多项修复已存在于起始工作区；本轮没有把它们算成自己的修复。

产品的核心问题是三个事实长期混用：引擎有适配器、当前执行环境可以访问、最终文件已经交付。另有三种生命周期混用：应用登录、第三方会话和页面请求。它们应分别有明确的状态所有者和恢复规则。

### 新改动中已确认并修复的缺陷

| 级别 | 位置 | 可复现的影响与修复 |
| --- | --- | --- |
| P1 | `backend/app/workers/runner/provider_cookie_agent.py:437` | 授权等待进入第二轮处理后，REFRESH 在探针线程同步执行，一个慢平台阻塞其他平台的 PROBE。复现测试先失败；现在整个授权等待期都使用已有的每平台有界工作槽，探针循环保持独立。 |
| P2 | `backend/app/workers/runner/provider_browser_bridge_store.py:117` | 首次创建 `.key` 时先公开空文件、再写 32 字节；并发 Native Host 会读到空密钥。两项回归均先失败。改为跨进程互斥初始化和完整临时文件原子发布，已有密钥不重建。 |
| P2 | `backend/tests/unit/workers/canary/test_fixed_cases.py:44` | 新测试把视频号从 `browser_session_providers()` 契约移除，但该集合包括专用元宝浏览器来源，导致全量门禁确定失败。恢复集合语义，不通过删除生产能力使测试变绿。 |

另修正浏览器授权组件中的同步顺序：`provider-authorization-dialog.tsx:166` 原先丢弃同步 Promise，失败也创建授权事务；现在等待相关联的 ACK，失败不开始事务，关闭后的迟到 ACK 不续接。当前服务端动作映射不会返回 `browser_session`，因此该组件分支的回归通过显式能力夹具验证，不把它认定为默认托管下载线路的已发生故障。

### 原有 Web 缺陷及本轮修复

- 请求层 catch 同时包住 Refresh 和业务重放，网络错误、429/503、重放后的 403 都可能触发 `window.location.replace`。现在请求层只报告经确认的会话失效，业务重放错误正常返回，由身份层和路由层分别管理身份与导航。
- 首次 `/auth/me` 网络失败被视为没有用户。现在身份有 `unknown / authenticated / anonymous`，请求中和请求错误单独保存；未知状态原地重试，只有确定 anonymous 才进入登录页。
- 每次恢复同一用户都会清空任务 Socket 订阅。现在只在身份变化时重置；旧身份响应不能刷新、重放或覆盖新身份。
- 迟到的恢复结果能够覆盖刚完成的登录，退出失败也被当作成功。现在身份操作使用 generation 保护；退出必须得到服务端确认，失败在当前页面反馈。
- `refresh_in_progress` 不能被当作刷新成功。现在先有界复查会话，仍未恢复则返回冲突，不清空身份、不盲目重放业务。

以上保留当前 HttpOnly Cookie 和服务端鉴权协议，不引入第二套登录通道。041 的 PostgreSQL 不透明 Web Session、统一业务查询缓存等仍是目标设计，尚未实施。客户端 generation 不能替代服务端处理跨标签 Cookie 轮换、撤销和账号切换的完整协议。

## 2. 平台能力应如何定义

本地已安装 yt-dlp（不是最新 upstream）的 `gen_extractor_classes()` 返回 **1,751 个提取器类**；当前默认进程登记 **23 个 Provider Profile**，实例配置还可能加入 PeerTube。这不等于 1,751 个平台，更不等于所有链接可下载。现有 Registry 已有 Generic 路线，产品标签中的“24”不是 yt-dlp 的技术上限。

目标继续使用现有 yt-dlp、可信插件与 Provider policy，增加一份与运行镜像对应的能力清单：

1. 镜像构建或受控启动时，从实际安装引擎枚举提取器，记录引擎 commit、插件版本和内容能力。清单只含非秘密元数据，不在每个 HTTP 请求中枚举提取器。
2. 既有 Provider Profile 作为策略覆盖：域名、内容类别、允许身份、格式与资源约束；管理员目录只管理名称、排序、启用意图，不假装创建了新的解析器。
3. 对候选 URL 使用引擎匹配能力与明确策略，未知来源只可进入有资源上限、无凭据的公开路线。动态识别不自动授予平台会话，不把 `_VALID_URL` 正则机械转换成完整域名列表。
4. 验证结果绑定 `engine + plugin + provider + content type + access context + egress`，分别保存 metadata、媒体和制品阶段证据。旧引擎、旧授权和旧出口的成功不能为新上下文背书。
5. 产品展示“近期验证可用”“需要授权”“暂时受限”“未验证”；引擎候选单独可搜索。某条链接失效不能直接宣布整个平台不可用。

新增常规站点只需引擎发现与通用准入；有特殊授权、媒体语义或反向链接风险时才新增 Profile/可信插件。引擎更新采用固定版本、候选矩阵、受控发布和回滚；禁止生产启动时无版本约束地更新。

## 3. Cookie 的根本设计：来源独立于发布

普通用户只粘贴链接、选择规格并观察任务。部署管理的第三方会话由服务端维护；个人授权必须绑定用户和授权范围。两者不能共用一个未隔离的全局账号。

会话来源具备独立的持久生命周期：Provider、所属管理域、账号主体、批准用途、版本、同步时间、已知失效时间、撤销状态。秘密进入现有隔离持久存储，API 只持有引用；Runner 每次操作只获得单 Provider 的只读租约。

维护流程为“在已有授权内获取 → 验证同一主体与必要字段 → 有界访问验证 → 原子发布新版本 → 新任务使用新版本 → 旧版本按租约回收”。刷新由单一维护者负责，每个来源单飞，失败退避，保留未失效旧版本；撤销和账号变化不得继续沿用旧材料。会话 Cookie 没有 expirationDate 也不代表永久有效。

自动化只适用于平台允许的刷新或已批准来源同步。首次同意、验证码、明确撤销需要一次必要操作；系统保存任务并续接，不能声称任何平台都能无条件自动取得 Cookie。

### 当前仍有的断点

- 文件来源的持久化与跨宿主发布已由 043 接通；浏览器桥的个人 `.snapshot` 仍不会自动登记为部署共享来源，不能将个人快照 ACK 当作托管线路可用证据。
- 扩展只有显式同步消息处理，没有完整的已批准 Provider 订阅、来源活性、同步时效和撤销 epoch 协议。当前 ACK 只证明这一批数据写入，不证明平台接受，也不证明持续维护。
- 启动时按瞬时来源健康删除路由的行为已在 043 修复：配置意图保留，运行时会话就绪独立检查，文件来源恢复后不要求重新部署。

043 已覆盖文件来源发布、短租约、Runner 运行就绪和启动配置意图。首次授权、上游会话续期与下载前意图自动续接仍需独立完成，不能将本地文件恢复等同于所有平台始终可下载。

## 4. 任务恢复与并发边界

继续使用 PostgreSQL、现有 Outbox、RabbitMQ 和 Worker。已有实现包含原子 job/outbox、幂等键、任务 lease/heartbeat、有界工作池、prefetch 和显式 ack；无需另建任务引擎。

下载前的解析和授权等待需要持久意图，沿用 040：用户一次提交生成 intent，记录格式偏好、批准来源、重试预算、下一次执行时间和取消状态；完成准备后幂等交接现有 job。刷新页面、授权回调重放和 API 重启都只恢复同一意图。

并发分别限制，不能用一个“并发数”覆盖所有资源：

| 层 | 必须控制的预算 |
| --- | --- |
| API | 用户/租户准入、活跃任务数、提交速率、连接池；重操作尽快返回持久任务 ID |
| 准备 Worker | 解析并发、同链接短时合并、授权等待上限、统一截止与重试预算 |
| Provider/来源 | 单来源刷新、账号/出口速率、429 Retry-After、熔断恢复的有限试探 |
| 下载 Runner | 同时执行数、字节/时长、磁盘水位、总带宽、子进程组取消 |
| 转码/分析 | 独立 CPU/内存预算和队列，避免耗尽下载处理资源 |

生产者确认和消费者确认是两个独立边界；重投递必须允许，数据库约束和租约负责防止重复业务结果。任务状态提交后才 ack；制品验证和原子提交前不能报告成功。重试预算统一计算，不能由浏览器、API、Runner 各自重试放大上游流量。

容量由实际服务时间和瓶颈决定：目标并发至少需要测量任务到达率 × 平均执行时间，并分别核对带宽、CPU、内存、磁盘及平台限流。10/50/100 等测试档位只能是测试输入，不能直接宣传为容量。

## 5. Web 连续性

本轮已把身份判定集中到根 AuthProvider。下一步处理业务数据：在稳定根布局设置统一查询缓存，按 owner 与查询参数隔离，返回页面使用有效缓存、后台校验；账号变化清理和取消旧查询。列表与详情按实际变更失效，Socket 重连后以 HTTP 快照收敛。

首次没有内容时显示局部骨架；已有内容刷新失败保留内容和操作上下文。加载边界只包需要等待的区域。不能通过固定延时、隐藏 spinner 或忽略错误来掩盖页面卸载。

本轮浏览器验证的 history/providers 切换保留了 header 节点，没有整页导航，也没有额外的身份恢复请求；断网恢复在原路由完成。该证据只覆盖身份与布局，不证明所有页面的数据加载、滚动、输入草稿和首次进入时都已消除闪烁。

## 6. 高可用验收与落地次序

单宿主 Compose 是当前运行边界，不能承诺宿主故障时仍可用。副本数大于一也不自动解决 PostgreSQL、RabbitMQ、Redis、MinIO 或会话来源的单点。真正跨宿主高可用需要明确状态存储复制、备份恢复、调度、入口切换和 RPO/RTO，并单独设计共享工作目录/对象存储交接；不得把当前本地 volume 当成跨主机共享文件系统。

按完整纵向用例实施：

1. 收敛本轮已复现的身份、并发、同步确认缺陷，冻结对应状态语义。
2. 以一个已批准 Provider 接通唯一持久来源、原子轮换、同主体校验、失效与撤销、同一路线恢复；证明正常重建不丢失有效来源，再扩展三个问题平台。
3. 接入持久下载意图和幂等恢复，前端仅观察，不由页面回调拥有任务进度。
4. 从实际引擎生成候选能力清单，关联现有策略与分阶段证据；更新平台目录和产品文案。
5. 实施页面缓存与加载边界；测量业务端到端延迟、无动作完成率、授权假阳性、重复执行、队列年龄与恢复耗时。
6. 在隔离数据上做负载和故障矩阵，达到明确门槛后才发布容量/可用性结论。

发布门槛至少包括：重建 API/Runner 后来源可用；来源轮换无需重建；撤销不复活；授权期间其他平台可用；重复消息只有一份业务结果；Worker 中断后租约恢复；数据库/队列短暂故障不丢已受理任务；业务成功只对应已验证制品；网络失败不跳登录；旧账号响应不覆盖新账号；移动端恢复可操作。真实 Provider 样本需分别验证 metadata 和完整媒体。
