# 工作流编排

本文规定 Temporal、RabbitMQ 与 PostgreSQL 的职责划分。同一业务只有一个执行所有者。

## 执行所有者

| 链路 | 执行者 | 业务事实与恢复 |
| --- | --- | --- |
| 解析意图 | Temporal `InspectionWorkflow`（`ff-inspect`，worker 内） | 单个 resolve Activity，120 秒总期限与取消；PostgreSQL 保存意图、结果与执行上下文 |
| Skill 分析 | Temporal 分析 Workflow（`ff-skill`，宿主 AI Worker） | AnalysisJob／Run／Step、固定来源与方法、执行所有权；结果未知不自动再次调用 |
| 下载、导入、报告发布 | RabbitMQ 消费者（worker 内） | 幂等消费、PostgreSQL lease/heartbeat、有限排空与 DLQ |
| 实时状态 | RabbitMQ fan-out | PostgreSQL 状态与版本是事实来源 |

- API 在同一事务保存业务记录、配额与 Outbox；dispatcher 按确定的 Workflow ID 直接启动 Temporal，不经 RabbitMQ 中转。
- `ff-inspect` 与 `ff-skill` 各自限制并发，不是额外容器。容器内 Worker 通过 `TEMPORAL_HOST`／`TEMPORAL_PORT` 连接，宿主 Worker 通过 `TEMPORAL_ADDRESS` 连接。
- 解析不维护策略、尝试、预算或会话账本；Temporal History 只含 ID、状态与必要版本，不保存 URL、Cookie、Key、完整 Prompt、媒体或原始模型输出。

## 解析与取消

- Workflow ID 为 `inspect/<intent_id>/<generation>`。resolve Activity 读取业务记录，按 Registry 阶梯执行，并原子保存 inspection、formats 与 `ready`。
- 客户端以意图 ID 查询、取消、刷新与交接；HTTP 不暴露 Temporal Run ID。
- 取消或超期时，业务事务写入 `cancelling` 与 Outbox；确认 Temporal 取消与对应 Runner 清理后才写 `cancelled` 或 `expired`。确认失败保留待确认状态，由原 Outbox 重投。
- Activity 的基础设施恢复沿用原截止时间；Runner 终止整个进程组，队列与子进程都有期限。

## Skill 执行

- 模型调用前写 Step 日志；回执未知时禁止自动重发；取消与执行者丢失保留真实状态；迟到结果由执行所有权与当前状态拒绝。
- 固定的源快照、任务、执行步骤与报告是 PostgreSQL 事实；临时工作区不是恢复账本。
- 报告导出读取已保存结果，失败单独重做，不重新调用模型。
- 解析侧的清理不能删除分析的不确定调用保护；未知调用的占用不因取消或失败而删除。

## 幂等

- 启动确认丢失时，按相同 Workflow ID 查询并核对业务绑定；运行中的 ID 冲突不会创建第二个执行。
- PostgreSQL 唯一约束与当前状态控制业务幂等；已完成、已取消与已刷新的记录拒绝迟到结果。

## 验证

- 确定性测试覆盖单 Activity、取消、幂等、失败分类、执行上下文与 OpenAPI；`schema.sql` 在空隔离库与已有当前态库上重复应用。
- 真实平台按[解析引擎](14-解析引擎.md#12-冷启动矩阵)验证完整文件。健康检查、平台登记、fixture 与模型模拟不替代真实文件或真实模型验收。
