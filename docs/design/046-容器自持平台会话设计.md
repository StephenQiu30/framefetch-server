# 046 容器自持平台会话设计

日期：2026-09-28。状态：设计基线，已评审（2026-09-28），实现中（S1–S5、S8 代码完成）；2026-09-28 修订 §6.1：登录态来源改为 Chrome 扩展。需求见 [PRD](../prd/046-容器自持平台会话PRD.md)，执行见 [Plan](../plan/046-容器自持平台会话Plan.md)。

本文取代 043（已删除，Git 历史可查） 的“来源取得与刷新”、044 Design 中宿主浏览器桥接部分，以及 [035](035-平台访问与会话恢复能力设计.md) 中视频号宿主专用元宝浏览器的运行模型。043 的持久加密、条件写入和撤销墓碑原则保留，并迁移到本文的数据模型。

## 1. 设计原则

1. **会话属于部署，不属于宿主进程**。服务端只有容器；登录态来源是部署者 Chrome 中的帧取扩展，宿主不运行本项目进程。
2. **登记即强制**。站点存在会话记录，就只能走账号路线；不可用时明确失败，不降级为匿名。
3. **一种机制覆盖所有站点**。平台差异只体现在注册表数据（附属域、登录校验、权益边界、动态头插件），不体现在拓扑中。
4. **身份一致**。同一站点的 Cookie、PO Token 和媒体请求使用同一出口。
5. **凭据按任务发放**。执行者不持有常驻凭据。

## 2. 拓扑

```
│ 设备令牌（可吊销）          │        │        │ 读写（唯一持密钥者）  │ 只读非秘密列       │
└──────────────────────────┘        │  ┌─────┴──────┐        ┌─────┴─────┐ 下载 Worker  │
                                    │  │session-broker│◀──────│    API    │──────────┐   │
                                    │  └──┬───────▲──┘ 状态   └───────────┘          │   │
                                    │ 种子│       │新 jar                   任务（HMAC）│   │
                                    │     ▼       │                                   ▼   │

                                    │  │ Chromium      │                  │ yt-dlp       ││
                                    │  │ /profiles/<站点>│   租约 ─────────▶│ tmpfs jar    ││
                                    │  └──────┬────────┘                  └──────┬───────┘│
                                    │         └──── 按站点出口 ─── egress-proxy ──┘ + bgutil │
                                    └────────────────────────────────────────────────┘
```

| 服务 | 职责 | 可访问 | 不可访问 |
| --- | --- | --- | --- |
| `session-broker`（由 `provider-sources` 改造） | 唯一持有 `SITE_SESSION_ENCRYPTION_KEY`；读写 `site_sessions`；向浏览器下发种子、接收刷新后的 jar；向 Runner 签发单任务租约；维护状态机 | PostgreSQL、`session_net`、`runner_rpc_net` | 外网、浏览器、对象存储、队列 |
| `session-browser`（新增） | 每站点一个持久 Chromium Profile；初始化、验证、保活、导出 jar、按任务生成动态头 | `session_net`、按站点出口 | 数据库、密钥、`runner_rpc_net` 以外的内部服务 |
| `session-runner`（替代 4 个 operator runner） | 与 `media-runner` 同镜像，`RUNNER_ACCESS_MODE=session`；按任务取得租约后执行 yt-dlp | `runner_rpc_net`、按站点出口、`youtube_pot_net` | 数据库、密钥、常驻 Cookie |
| `media-runner`、`douyin-guest-runner` | 不变：匿名和访客路线 | 不变 | 不变 |

`session-browser` 是后端 Dockerfile 的 `session-browser` 构建目标：同一 Python 基础镜像，依赖组 `browser`（`playwright==1.63.0`）固定 Chromium 版本，Playwright 持久化上下文直接管理每站点 Profile、代理与 Cookie，不自写 CDP 客户端。容器以非 root、`cap_drop: ALL`、只读根文件系统运行，`/tmp` 与 `$HOME` 为 tmpfs，Profile 位于命名卷 `site_session_profiles`（`/profiles/<site>`，0700）。RPC 端口 19300 只在 `session_net` 上，不发布宿主端口；出口只能经 `runner_egress_net` 上的 egress-proxy。每次操作打开对应 Profile、结束即关闭浏览器，进程内同一站点串行、全部站点并发 2、单次操作 60 s。

## 3. 站点标识与注册表

### 3.1 站点

`site` 是会话的唯一键，是一个域名。已知平台使用注册表声明的键；其他站点取链接主机名，按项目锁定版本的 Public Suffix List（`tldextract` 离线快照，含私有后缀）计算可注册域名，例如 `media.sub.example.co.uk → example.co.uk`。已知平台的键可以比可注册域名更具体：视频号为 `weixin.qq.com`，腾讯视频为 `v.qq.com`，两者都在 `qq.com` 下但属于不同身份，因此不能统一取可注册域名。

以下情况拒绝登记：IP 字面量、`localhost` 等单标签名、PSL 未收录的后缀（`.internal`、`.test` 等）、公共后缀本身（含 `github.io` 这类私有后缀）。PSL 随依赖锁定升级，运行期不联网、不写缓存。

### 3.2 已知平台注册表

URL 主机和 Cookie 域继续由现有 `ProviderProfile`（`hosts`、`cookie_domain_allowlist`）维护，不另存一份。站点会话注册表（`app/services/site_sessions.py`）只声明会话专有字段：

| 字段 | 含义 | 示例（YouTube） |
| --- | --- | --- |
| `site` | 会话键 | `youtube.com` |
| `provider_key` | 既有平台键；URL 经 `ProviderProfile.hosts` 命中该平台即使用本会话 | `youtube`（覆盖 `youtu.be`、`m.youtube.com`、`youtube-nocookie.com` 等） |
| `required_cookie_names`／`requirement` | 导入时的必需 Cookie 校验 | `SAPISID`、`__Secure-3PSID` 等任一 |
| `login_probe` | 登录校验方式 | `youtube_logged_in`：`ytcfg.LOGGED_IN === true` |
| `keepalive_url` | 保活访问的轻量页面 | `https://www.youtube.com/feed/you` |
| `entitlement` | 内容权益边界 | `public_only`；优酷、腾讯视频为 `account_entitled_full_video`（032） |
| `header_plugin` | 按任务生成动态头的浏览器插件 | 无；视频号为 `yuanbao` |

首期条目覆盖现有全部账号会话平台：YouTube、抖音、小红书、X、Instagram、Facebook、Reddit、Pinterest、优酷、腾讯视频、视频号（键 `weixin.qq.com`，Cookie 来自 `yuanbao.tencent.com`，另见 §6.4）。除 YouTube 外，`login_probe` 首期为 `cookies_retained`，S4 按真实页面补充各平台的强校验。

`app/integrations/site_session_catalog.py` 负责组合：URL 先经 `ProviderProfile` 解析，命中已知条目则取该条目和平台的 Cookie 域；否则按可注册域名得到未知站点。服务层不依赖 `workers`（架构测试约束），组合只放在 integrations。

### 3.3 未知站点

部署者在扩展中为某个页面的站点启用同步时，注册表中没有该站点，则以默认条目登记：Cookie 域只有该站点、`login_probe=cookies_retained`（导航后种子 Cookie 仍然存在且未被服务端清除）、`keepalive_url=https://<site>/`、`entitlement=public_only`、无插件。弱校验的限制在状态页如实显示为“已保持，未证明登录”。真正的可用性以首次执行结果为准，执行得到认证类错误时进入 `degraded`。

### 3.4 URL 到路线

API 解析、下载意图与 Canary 用同一个 `SiteSessionRoutes`（`app/integrations/site_session_catalog.py`）：

1. 用 `site_target_for_url` 把 URL 映射到 `site`（§3.2）。
2. `site_sessions` 中存在该站点记录且状态不是 `revoked` → 强制使用会话路线，访问模式为 `OPERATOR_MANAGED`，交给唯一的 `session-runner`；策略沿用 `OPERATOR_PUBLIC`，条目 `entitlement` 为账号权益时为 `PERSONAL_ENTITLED`。客户端显式请求其他策略时拒绝，不回退匿名。状态不是 `ready` 时由 Runner 返回 `provider_session_not_ready`（HTTP 503）。
3. 不存在记录 → 走既有公开或访客路线（044）。

下载 Worker 不重新选路：它按冻结的访问上下文把 URL 交回原模式的 Runner 重新取上下文（`POST /internal/v1/context` 携带 URL，而不是平台键，因为未适配站点的平台键都是 `generic`）。Runner 的命令构建不再按平台目录判断能否携带 Cookie：匿名 Runner 一律拒绝，会话与访客 Runner 由各自的上下文准入。

`revoked` 记录保留墓碑但不强制路由，撤销后站点回到公开路线，这是部署者的显式操作。决策只读非秘密列，不读环境变量。`RUNNER_DEFAULT_ACCESS_POLICIES`、`RUNNER_OPERATOR_BASE_URLS` 中与会话有关的内容全部删除。

## 4. 数据模型

`backend/sql/schema.sql` 新增下表；`provider_session_sources` 和 `provider_authorizations` 在 S8 与旧代码同一发布删除，避免 S1–S7 期间运行中的旧链路失去表：

```sql
CREATE TABLE IF NOT EXISTS site_sessions (
    site VARCHAR(253) PRIMARY KEY,
    provider_key VARCHAR(32),
    state VARCHAR(24) NOT NULL,
    seed_revision BIGINT NOT NULL,
    jar_version BIGINT NOT NULL DEFAULT 0,
    ciphertext BYTEA,
    egress_route VARCHAR(64) NOT NULL,
    seeded_at TIMESTAMPTZ NOT NULL,
    refreshed_at TIMESTAMPTZ,
    verified_at TIMESTAMPTZ,
    last_error_code VARCHAR(64),
    consecutive_failures INTEGER NOT NULL DEFAULT 0,
    state_changed_at TIMESTAMPTZ NOT NULL,
    CONSTRAINT ck_site_sessions_state CHECK (
        state IN ('seeded', 'verifying', 'ready', 'degraded', 'reseed_required', 'revoked')
    ),
    CONSTRAINT ck_site_sessions_seed_revision CHECK (seed_revision > 0),
    CONSTRAINT ck_site_sessions_jar_version CHECK (jar_version >= 0),
    CONSTRAINT ck_site_sessions_revoked CHECK ((state = 'revoked') = (ciphertext IS NULL))
);
ALTER TABLE site_sessions
    ADD COLUMN IF NOT EXISTS consecutive_failures INTEGER NOT NULL DEFAULT 0;
```

- 密文用 Fernet（`SITE_SESSION_ENCRYPTION_KEY`）加密，关联数据绑定 `site|seed_revision|jar_version`。
- 所有写入都是条件写入：导入以 `seed_revision` 为期望值，保活以 `(seed_revision, jar_version)` 为期望值。迟到的保活结果不能覆盖新导入，也不能复活撤销。
- API 仓储只 `SELECT` 非秘密列，由仓储测试断言。
- 旧表不迁移：`provider_session_sources` 中的来源最长 15 分钟有效，事实上已不可用；上线后由扩展重新同步。设备与设备授权两张表见 §6.1。

## 5. 状态机

```
 seed ──▶ seeded ──▶ verifying ──ok──▶ ready ◀──保活/执行成功── degraded
                        │                │  │                       ▲
                        │ 认证失败        │  └──保活/执行认证类失败──┘
                        ▼                ▼ degraded 连续 3 次或 24 h 未恢复
                 reseed_required ◀───────┘
 任何状态 ──revoke──▶ revoked（墓碑）          任何状态 ──seed──▶ seeded（新 seed_revision）
```

| 事件 | 转换 | 说明 |
| --- | --- | --- |
| 浏览器载入种子并通过 `login_probe` | `seeded／verifying／degraded → ready` | 失败计数清零、记录 `verified_at`；导出的 jar 与当前不同才写入，`jar_version+1` |
| 保活或执行得到认证类错误（`credential_expired`、`credential_rejected`、`egress_challenged`） | `ready → degraded`；新导入停留在 `verifying` | `consecutive_failures+1`；执行错误由 Runner 经 broker 上报，PO Token、限流、网络和提取器错误不计入；进入 `degraded` 后下一次扫描立即保活复验 |
| 连续 3 次认证类失败，或进入 `degraded` 满 24 h | `→ reseed_required` | 24 h 从进入 `degraded` 算起：同状态刷新不改 `state_changed_at` |
| `login_probe` 明确显示已退出，或执行得到 `credential_revoked` | `→ reseed_required` | 不重试 |
| 存储的密文无法解密（密钥更换） | `→ reseed_required`（`session_undecryptable`） | |

**告警**：项目没有独立的管理员通知通道。进入 `reseed_required` 的条件写入只有一个赢家，由它输出一条 WARNING 日志（站点、修订、原因，无秘密）；持久状态本身由 S7 的管理员状态页展示。纯函数规则位于 `app/services/site_session_lifecycle.py`。

`provider_session_not_ready` 的用户文案：“该平台的部署会话暂不可用，请稍后重试。”管理员页面显示具体状态和处理动作。

## 6. 流程

### 6.1 登录态来源：帧取 Chrome 扩展

2026-09-28 修订：原宿主导入命令被 macOS 隐私保护阻断（只有 Chrome 自身能打开其数据目录，PRD §1.2），改为由 Chrome 内的扩展通过 `chrome.cookies` 取得 Cookie。Chrome 自己解密，不需要钥匙串或“完全磁盘访问权限”，任何桌面系统都适用。

**组成**：仓库根目录 `extension/`，Manifest V3，纯 ES 模块，不需要构建。

| 文件 | 职责 |
| --- | --- |
| `manifest.json` | 权限 `cookies`、`alarms`、`storage`、`activeTab`；`host_permissions` 为全部已知平台 Cookie 域与 `http://localhost/*`、`http://127.0.0.1/*`；`optional_host_permissions` 为 `https://*/*`、`http://*/*`（自定义帧取地址与未知站点，按次由用户授权） |
| `background.js` | Service Worker：`chrome.alarms` 每 5 min 同步一次；设备授权轮询 |
| `sync.js` | 纯函数：同步计划 + 本地状态 → 需要提交的站点与 Cookie（可单测） |
| `popup.html`／`popup.js` | 连接帧取、站点列表与状态、为当前页面站点启用、撤销后重新启用 |

契约测试断言 `host_permissions` 覆盖注册表中全部已知 Cookie 域，避免两份清单漂移。

**设备授权**（RFC 8628 设备授权的精简版，令牌只在服务端存哈希）：

1. 部署者在扩展中填写帧取地址（默认 `http://localhost:8101`，非回环地址时请求该来源的可选主机权限）并点击“连接”。
2. 扩展调用 `POST /api/site-session-devices/authorizations`（无需登录，限流）提交设备名，得到 `device_code`（32 字节随机，服务端只存 SHA-256）、`user_code`（`XXXX-XXXX`）、确认页地址、10 min 有效期和 5 s 轮询间隔，并打开确认页。
3. 管理员在已登录的帧取确认页核对设备名与 `user_code`，点击“批准”（`POST /api/admin/site-session-devices/authorizations/{user_code}/approve`，沿用 Cookie 登录与来源校验）。
4. 扩展轮询 `POST /api/site-session-devices/tokens`：未批准返回 `authorization_pending`，过期返回 `authorization_expired`；批准后一次性返回设备令牌（32 字节随机），授权记录随即作废。令牌存于扩展的 `chrome.storage.local`，服务端只存哈希，管理员可吊销。

```sql
CREATE TABLE IF NOT EXISTS site_session_devices (
    id UUID PRIMARY KEY,
    name VARCHAR(80) NOT NULL,
    token_hash BYTEA NOT NULL UNIQUE,
    approved_by UUID NOT NULL,
    created_at TIMESTAMPTZ NOT NULL,
    last_seen_at TIMESTAMPTZ,
    revoked_at TIMESTAMPTZ
);
CREATE TABLE IF NOT EXISTS site_session_device_authorizations (
    device_code_hash BYTEA PRIMARY KEY,
    user_code VARCHAR(9) NOT NULL UNIQUE,
    device_name VARCHAR(80) NOT NULL,
    expires_at TIMESTAMPTZ NOT NULL,
    approved_by UUID,
    approved_at TIMESTAMPTZ,
    consumed_at TIMESTAMPTZ
);
```

**同步**（设备令牌以 `Authorization: Bearer` 携带；这些路径不使用 Cookie，豁免浏览器来源校验）：

1. `GET /api/site-session-devices/plan` 返回同步间隔与站点列表：每个已知平台条目和每条已有记录给出 `site`、`cookie_domains`、`state`（无记录为空）和 `wanted`。`wanted` 为真当且仅当：已知平台尚无记录，或状态为 `reseed_required`。`revoked` 的站点 `wanted` 为假。计划不含任何秘密。
2. 扩展对 `wanted` 站点，以及用户在扩展中显式启用的未知站点和“撤销后重新启用”的站点，用 `chrome.cookies.getAll` 按 Cookie 域读取，只保留域名落在该站点 Cookie 域内的条目，计算指纹（按域、路径、名称排序后的 SHA-256）。与上次提交该站点的指纹相同则跳过：平台已拒绝的同一组 Cookie 不重复提交，Chrome 重新登录或轮换后自然变化。
3. `POST /api/site-session-devices/seeds` 提交 `{site, explicit, cookies:[{domain, name, value, path, secure, httpOnly, expirationDate}]}`（最多 300 条、256 KiB）。API 不解析语义、不落盘、不记录请求体，只做形状与大小校验后经签名 RPC 转发给 broker 的 `POST /internal/v1/site-sessions/seed`（新增密钥 `SITE_SESSION_SEED_SECRET`，经既有 `runner_rpc_net`），并更新设备 `last_seen_at`。
4. broker 用 `site_target_for_host` 解析站点，只保留站点 Cookie 域内、有值、字段安全、未过期的 Cookie，要求至少一个持久 Cookie 且满足注册表必需规则，否则返回 `not_logged_in`。记录为 `revoked` 且 `explicit` 为假时返回 `revoked`；记录处于 `seeded`／`verifying`／`ready`／`degraded` 且 `explicit` 为假时返回 `unchanged`（容器端的轮换只由会话浏览器负责，避免两个写者）。其余情况用 `SITE_SESSION_ENCRYPTION_KEY` 加密（绑定 `site|seed_revision|0`）并条件写入：状态 `seeded`、`seed_revision+1`、`jar_version=0`，返回 `seeded`。

`seed` 命令只保留 `status` 与 `revoke`（运维入口），`import` 子命令与 `chrome_reader.py` 删除。

### 6.2 容器初始化与恢复

broker 是唯一的调度者，浏览器只是被动的 RPC 服务（不连接 broker、不访问数据库）。broker 每 15 s 扫描 `site_sessions`：

| 记录状态 | 动作 |
| --- | --- |
| `seeded`、`verifying` | 条件写入 `seeded → verifying`，然后 `bootstrap`；浏览器不可达或返回 `unavailable` 时保持 `verifying`，下一次扫描重试 |
| `ready`、`degraded` 且保活到期 | `keepalive`；浏览器返回 `profile_missing` 时用数据库中最新 jar 重新 `bootstrap` |
| `degraded` 满 24 h | `→ reseed_required` |
| `revoked` | 调用浏览器 `forget` 删除 Profile，每个修订在进程内只成功一次 |

1. **身份**：浏览器每个进程生成一把 X25519 密钥，`identity` 返回公钥。broker 每次 `bootstrap` 都重新取公钥（浏览器重启后公钥会变）。
2. **下发**：jar 封装给浏览器公钥，关联数据 `site-session-bootstrap:v1:{site}:{seed_revision}`。
3. **回传**：每次请求附带 broker 的一次性回复公钥；浏览器导出的 jar 封装给它，关联数据 `site-session-export:v1:{site}:{seed_revision}`。
4. **写入**：只有 `verified` 结果的 jar 才会写入，且与当前 jar 不同才写，条件为 `(seed_revision, jar_version)`；迟到的旧修订结果被拒绝。
5. **并发**：同一站点在 broker 进程内串行（每站点锁），全部站点合计最多 2 个并发浏览器操作；单个站点失败不影响其余站点的扫描。

Profile 卷存在时，重启后 Chromium 直接使用磁盘上的 Cookie，只需一次保活。Profile 卷丢失时浏览器返回 `profile_missing`，broker 从数据库最新 jar 重建。两者都不需要宿主参与，满足 PRD NFR-01。

两条内部通道使用独立的 HMAC 密钥：`SITE_SESSION_RPC_SECRET`（Runner → broker）与 `SITE_SESSION_BROWSER_SECRET`（broker → 浏览器），签名头为 `X-Session-Timestamp／Nonce／Signature`，60 s 时间窗与进程内防重放。Runner 无法冒充 broker 调用浏览器。

### 6.3 保活

broker 为每个 `ready`／`degraded` 站点安排保活：首次到期时间为 `max(seeded_at, verified_at, refreshed_at) + 30 min ± 5 min`，之后每次执行后重新抽取抖动；进入 `degraded` 时立即到期。浏览器执行：导航到 `keepalive_url`（等待 `load`）→ 登录判定 → 导出 jar。

| 结果 | 判定 |
| --- | --- |
| `auth_failure`（`egress_challenged`） | 主文档返回 403 或 429 |
| `verified`／`logged_out` | YouTube：`ytcfg.get('LOGGED_IN')`；视频号：元宝页面 `localStorage` 中存在 `userId` 与 `token`；其他站点：该站点 Cookie 域内的持久 Cookie 仍满足注册表必需规则（未知站点为“至少一个持久 Cookie”） |
| `unavailable` | 导航超时、网络或浏览器错误 |
| `profile_missing` | 保活时站点 Profile 目录不存在 |

导出的 jar 只含站点 Cookie 域内有值的 Cookie，按域、路径、名称排序后序列化，保证未变化时字节一致，broker 才能正确判断“是否轮换”。

顶层导航用 Playwright `page.route` 拦截：主框架的导航请求只允许站点 Cookie 域及 `keepalive_url` 主机，子资源与子框架放行。所有流量经 egress-proxy，私网目的地由既有 squid ACL 阻断。

### 6.4 执行（Runner 租约）

1. 下载 Worker／API 按 §3.4 选出 `site_session` 路线，把任务发给 `session-runner`（沿用 HMAC 调用），访问上下文的 `credential_version_id` 冻结为 `{site}:{seed_revision}`。
2. Runner 为本任务生成内存中的 X25519 临时密钥对，向 broker 请求 `lease(task_id, site, seed_revision, runner_public_key)`。
3. broker 检查状态为 `ready` 且 `seed_revision` 一致，否则返回 HTTP 409 `provider_session_not_ready`（由上层重新解析）；然后用 X25519 + HKDF + ChaCha20-Poly1305（`app/workers/session/sealing.py`，每次封装使用新的发送方临时密钥）封装当前 jar，关联数据为 `site-session-lease:v1:jar:{task_id}:{site}:{seed_revision}:{expires_at}`，有效期 10 min。接口为 `POST /internal/v1/site-sessions/lease`，失败上报为 `POST /internal/v1/site-sessions/failures`（broker 端口 19200）。
4. Runner 解封后写入独占 tmpfs 的 `0600` jar，执行 yt-dlp，结束或取消时删除。跨副本单站点并发 1 沿用 Redis 凭据租约，键为 `(site, seed_revision)`。
5. yt-dlp 退出后，Runner 把 `--cookies` 回写的 jar 丢弃，不回传；Cookie 轮换只由浏览器负责，避免两个写者。执行得到认证类错误时，Runner 向 broker 报告 `(site, seed_revision, error_code)`。

访问上下文冻结 `site + seed_revision`，与 043 一致：保活刷新不使旧 inspection 失效，重新导入会使其失效。

**视频号**：`header_plugin=yuanbao` 的站点在第 3 步由 broker 额外请求浏览器 `headers(site, seed_revision, task_id, expires_at, runner_public_key)`。浏览器在该站点 Profile 中打开元宝页面，按原 `yuanbao_session` 的页面脚本读取身份并生成动态头，载荷为 JSON `{"hy_user","hy_token","headers"}`（最多 32 个、无换行的 ASCII 头），直接封装给 Runner 公钥（关联数据种类为 `headers`）；broker 只转发密文，看不到明文。浏览器不可用时租约返回 409。宿主专用元宝目录、LaunchAgent 和本机加密队列全部删除。

### 6.5 出口

`SITE_EGRESS_ROUTES`（JSON，`{"youtube.com":"http://…"}`，默认 `RUNNER_EGRESS_PROXY`）替代 `RUNNER_PROVIDER_EGRESS_PROXIES`。`egress_route` 在种子写入时记录；浏览器、Runner 和 bgutil（YouTube）都按记录中的路由选择出口。路由改变视为身份改变，需要重新补种。

## 9. 安全分析

| 威胁 | 控制 |
| --- | --- |
| 浏览器被恶意页面利用 | 顶层导航限于已登记站点；无数据库、无密钥、无 RPC 访问内部业务；非 root、只读根、`cap_drop: ALL`；Chromium 随镜像固定版本升级 |
| Runner 被利用 | 只拿到当前任务单站点的 jar，10 min 过期，临时私钥只在内存；无法向 broker 申请其他站点（broker 按任务路由校验 `site`） |
| broker 被利用 | 不访问外网，不解析媒体；持有全部密文和密钥，是最高价值目标，只在 `session_net`／`runner_rpc_net` 上监听且需 HMAC |
| 扩展读取过多 | 只读取同步计划与用户显式启用站点的 Cookie 域；未知站点需逐站点授予主机权限；Cookie 不在扩展中持久化，只发往已连接的帧取地址；broker 按 §3.1 拒绝私网与公共后缀 |
| 设备令牌泄露 | 服务端只存哈希，管理员可吊销；令牌只能读取不含秘密的计划和提交种子，不能读取任何会话；提交仍经 broker 校验站点与 Cookie 域 |
| 恶意页面诱导批准 | 批准需要已登录的管理员并通过既有来源校验；确认页显示设备名与 `user_code`，与扩展中显示的一致才批准；授权 10 min 过期、一次性 |
| 会话被用于越权内容 | `entitlement=public_only` 的站点仍执行既有内容限制分类（private、会员、付费、DRM）并终止；账号会话不扩大权益 |
| 迟到写入复活撤销 | 条件写入 + `revoked` 墓碑，与 043 相同 |
