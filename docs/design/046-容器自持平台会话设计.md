# 046 容器自持平台会话设计

日期：2026-09-28。状态：设计基线，已评审（2026-09-28），实现中（S1、S2 代码完成）。需求见 [PRD](../prd/046-容器自持平台会话PRD.md)，执行见 [Plan](../plan/046-容器自持平台会话Plan.md)。

本文取代 [043](043-跨宿主平台来源自动恢复.md) 的“来源取得与刷新”、044 Design 中宿主浏览器桥接部分，以及 [035](035-平台访问与会话恢复能力设计.md) 中视频号宿主专用元宝浏览器的运行模型。043 的持久加密、条件写入和撤销墓碑原则保留，并迁移到本文的数据模型。

## 1. 设计原则

1. **会话属于部署，不属于宿主进程**。运行期只有容器，宿主机只参与一次性导入。
2. **登记即强制**。站点存在会话记录，就只能走账号路线；不可用时明确失败，不降级为匿名。
3. **一种机制覆盖所有站点**。平台差异只体现在注册表数据（附属域、登录校验、权益边界、动态头插件），不体现在拓扑中。
4. **身份一致**。同一站点的 Cookie、PO Token 和媒体请求使用同一出口。
5. **凭据按任务发放**。执行者不持有常驻凭据。

## 2. 拓扑

```
            宿主（仅一次）                              Compose（常驻）
┌──────────────────────────┐        ┌────────────────────────────────────────────────┐
│ session seed 命令          │ 种子   │  PostgreSQL（既有）  site_sessions               │
│ 读取本机 Chrome 指定站点    ├──────▶│        ▲                     ▲                   │
│ Cookie → 加密登记           │        │        │ 读写（唯一持密钥者）  │ 只读非秘密列       │
└──────────────────────────┘        │  ┌─────┴──────┐        ┌─────┴─────┐ 下载 Worker  │
                                    │  │session-broker│◀──────│    API    │──────────┐   │
                                    │  └──┬───────▲──┘ 状态   └───────────┘          │   │
                                    │ 种子│       │新 jar                   任务（HMAC）│   │
                                    │     ▼       │                                   ▼   │
                                    │  ┌──────────┴───┐   单任务加密租约   ┌──────────────┐│
                                    │  │session-browser│ ◀── 动态头 ───── │session-runner││
                                    │  │ Chromium      │                  │ yt-dlp       ││
                                    │  │ /profiles/<站点>│   租约 ─────────▶│ tmpfs jar    ││
                                    │  └──────┬────────┘                  └──────┬───────┘│
                                    │         └──── 按站点出口 ─── egress-proxy ──┘ + bgutil │
                                    └────────────────────────────────────────────────┘
```

| 服务 | 职责 | 可访问 | 不可访问 |
| --- | --- | --- | --- |
| `session-broker`（由 `provider-sources` 改造） | 唯一持有 `SITE_SESSION_ENCRYPTION_KEY`；读写 `site_sessions`；向浏览器下发种子、接收刷新后的 jar；向 Runner 签发单任务租约；维护状态机 | PostgreSQL、`session_net`、`runner_rpc_net` | 外网、浏览器、对象存储、队列 |
| `session-browser`（新增） | 每站点一个持久 Chromium Profile；初始化、验证、保活、导出 jar、按任务生成动态头 | `session_net`、按站点出口 | 数据库、密钥、`runner_rpc_net` 以外的内部服务 |
| `session-runner`（替代 4 个 operator runner） | 与 `media-runner` 同镜像，`RUNNER_ACCESS_MODE=session`；按任务取得租约后执行 yt-dlp | `runner_rpc_net`、按站点出口、`youtube_pot_net` | 数据库、密钥、常驻 Cookie |
| `media-runner`、`douyin-guest-runner` | 不变：匿名和访客路线 | 不变 | 不变 |

`session-browser` 使用固定版本的 Chromium（Debian 仓库或 Playwright 基础镜像，锁定 digest），以 `--headless=new`、非 root、`cap_drop: ALL`、只读根文件系统运行，Profile 位于命名卷 `site_session_profiles`。浏览器 RPC 只监听 `session_net`，不发布宿主端口；CDP 端口只绑定容器内回环地址。

## 3. 站点标识与注册表

### 3.1 站点

`site` 是会话的唯一键，是一个域名。已知平台使用注册表声明的键；其他站点取链接主机名，按项目锁定版本的 Public Suffix List（`tldextract` 离线快照，含私有后缀）计算可注册域名，例如 `media.sub.example.co.uk → example.co.uk`。已知平台的键可以比可注册域名更具体：视频号为 `weixin.qq.com`，腾讯视频为 `v.qq.com`，两者都在 `qq.com` 下但属于不同身份，因此不能统一取可注册域名。

以下情况拒绝登记：IP 字面量、`localhost` 等单标签名、PSL 未收录的后缀（`.internal`、`.test` 等）、公共后缀本身（含 `github.io` 这类私有后缀）。PSL 随依赖锁定升级，运行期不联网、不写缓存。

### 3.2 已知平台注册表

URL 主机和 Cookie 域继续由现有 `ProviderProfile`（`hosts`、`cookie_domain_allowlist`）维护，不另存一份。站点会话注册表（`app/services/site_sessions.py`）只声明会话专有字段：

| 字段 | 含义 | 示例（YouTube） |
| --- | --- | --- |
| `site` | 会话键 | `youtube.com` |
| `provider_key` | 既有平台键；URL 经 `ProviderProfile.hosts` 命中该平台即使用本会话 | `youtube`（覆盖 `youtu.be`、`m.youtube.com`、`youtube-nocookie.com` 等） |
| `required_cookie_names`／`requirement` | 导入时的必需 Cookie 校验 | `SAPISID`、`__Secure-3PSID` 等任一 |
| `login_probe` | 登录校验方式 | `youtube_logged_in`：`ytcfg.LOGGED_IN === true` |
| `keepalive_url` | 保活访问的轻量页面 | `https://www.youtube.com/feed/you` |
| `entitlement` | 内容权益边界 | `public_only`；优酷、腾讯视频为 `account_entitled_full_video`（032） |
| `header_plugin` | 按任务生成动态头的浏览器插件 | 无；视频号为 `yuanbao` |

首期条目覆盖现有全部账号会话平台：YouTube、抖音、小红书、X、Instagram、Facebook、Reddit、Pinterest、优酷、腾讯视频、视频号（键 `weixin.qq.com`，Cookie 来自 `yuanbao.tencent.com`，另见 §6.4）。除 YouTube 外，`login_probe` 首期为 `cookies_retained`，S4 按真实页面补充各平台的强校验。

`app/integrations/site_session_catalog.py` 负责组合：URL 先经 `ProviderProfile` 解析，命中已知条目则取该条目和平台的 Cookie 域；否则按可注册域名得到未知站点。服务层不依赖 `workers`（架构测试约束），组合只放在 integrations。

### 3.3 未知站点

部署者用 `session seed --site example.com` 导入任意站点时，注册表中没有该站点，则以默认条目登记：Cookie 域只有该站点、`login_probe=cookies_retained`（导航后种子 Cookie 仍然存在且未被服务端清除）、`keepalive_url=https://<site>/`、`entitlement=public_only`、无插件。弱校验的限制在状态页如实显示为“已保持，未证明登录”。真正的可用性以首次执行结果为准，执行得到认证类错误时进入 `degraded`。

### 3.4 URL 到路线

API 与下载 Worker 用同一个 `SiteRouteResolver`：

1. 用 `site_target_for_url` 把 URL 映射到 `site`（§3.2）。
2. `site_sessions` 中存在该站点记录且状态不是 `revoked` → 路线为 `site_session`；状态不是 `ready` 时抛出 `provider_session_not_ready`。
3. 不存在记录 → 走既有公开或访客路线（044）。

`revoked` 记录保留墓碑但不强制路由，撤销后站点回到公开路线，这是部署者的显式操作。决策只读非秘密列，不读环境变量。`RUNNER_DEFAULT_ACCESS_POLICIES`、`RUNNER_OPERATOR_BASE_URLS` 中与会话有关的内容全部删除。

## 4. 数据模型

`backend/sql/schema.sql` 新增下表；`provider_session_sources` 和 `provider_authorizations` 在 S8 与旧代码同一发布删除，避免 S1–S7 期间运行中的旧链路失去表：

```sql
CREATE TABLE IF NOT EXISTS site_sessions (
    site VARCHAR(253) PRIMARY KEY,
    provider_key VARCHAR(32),
    state VARCHAR(24) NOT NULL,
    seed_revision BIGINT NOT NULL,
    jar_version BIGINT NOT NULL DEFAULT 0,
    ciphertext BYTEA,
    egress_route VARCHAR(64) NOT NULL,
    seeded_at TIMESTAMPTZ NOT NULL,
    refreshed_at TIMESTAMPTZ,
    verified_at TIMESTAMPTZ,
    last_error_code VARCHAR(64),
    state_changed_at TIMESTAMPTZ NOT NULL,
    CONSTRAINT ck_site_sessions_state CHECK (
        state IN ('seeded', 'verifying', 'ready', 'degraded', 'reseed_required', 'revoked')
    ),
    CONSTRAINT ck_site_sessions_seed_revision CHECK (seed_revision > 0),
    CONSTRAINT ck_site_sessions_jar_version CHECK (jar_version >= 0),
    CONSTRAINT ck_site_sessions_revoked CHECK ((state = 'revoked') = (ciphertext IS NULL))
);
```

- 密文用 Fernet（`SITE_SESSION_ENCRYPTION_KEY`）加密，关联数据绑定 `site|seed_revision|jar_version`。
- 所有写入都是条件写入：导入以 `seed_revision` 为期望值，保活以 `(seed_revision, jar_version)` 为期望值。迟到的保活结果不能覆盖新导入，也不能复活撤销。
- API 仓储只 `SELECT` 非秘密列，由仓储测试断言。
- 旧表不迁移：`provider_session_sources` 中的来源最长 15 分钟有效，事实上已不可用；上线后由部署者重新导入。

## 5. 状态机

```
 seed ──▶ seeded ──▶ verifying ──ok──▶ ready ◀──保活/执行成功── degraded
                        │                │  │                       ▲
                        │ 认证失败        │  └──保活/执行认证类失败──┘
                        ▼                ▼ degraded 连续 3 次或 24 h 未恢复
                 reseed_required ◀───────┘
 任何状态 ──revoke──▶ revoked（墓碑）          任何状态 ──seed──▶ seeded（新 seed_revision）
```

| 事件 | 转换 | 说明 |
| --- | --- | --- |
| 浏览器载入种子并通过 `login_probe` | `verifying → ready` | 同时导出一次 jar，`jar_version+1` |
| 保活或执行得到认证类错误（`credential_expired`、`credential_rejected`、`egress_challenged`） | `ready → degraded` | 执行错误由 Runner 经 broker 上报；PO Token 或网络类错误不计入 |
| `degraded` 下成功保活或执行 | `degraded → ready` | |
| `degraded` 连续 3 次失败或持续 24 h | `→ reseed_required` | 发出一次告警（沿用管理员通知通道），状态页给出导入命令 |
| `login_probe` 明确显示已退出 | `→ reseed_required` | 不重试 |

`provider_session_not_ready` 的用户文案：“该平台的部署会话暂不可用，请稍后重试。”管理员页面显示具体状态和处理动作。

## 6. 流程

### 6.1 一次性导入（宿主）

```bash
uv run python -m app.workers.session.seed [--env-file .env] import --site youtube.com [--profile "Profile 2"]
uv run python -m app.workers.session.seed status
uv run python -m app.workers.session.seed revoke --site youtube.com
```

1. 用 `site_target_for_host` 解析站点和注册表条目，得到需要读取的 Cookie 域集合；非法站点在读取 Chrome 前拒绝。
2. 用 `app/workers/session/chrome_reader.py` 读取 Chrome Profile（列表与显示名来自 `Local State`）。未指定 Profile 时：只有一个 Profile 含该站点登录就使用它；多个则列出“目录（显示名）”并退出，要求 `--profile`；任一 Profile 被拒绝读取则报告权限问题，不在其余 Profile 中猜测；都没有则报告未登录。
3. 只保留目标 Cookie 域内、有值、字段安全、未过期的 Cookie；要求至少一个持久 Cookie（纯会话 Cookie 随 Chrome 重启消失，不算持久登录），已知站点再满足注册表的必需 Cookie 规则。
4. 用 `SITE_SESSION_ENCRYPTION_KEY` 加密（绑定 `site|seed_revision|0`），条件写入 `site_sessions`：状态 `seeded`、`seed_revision+1`、`jar_version=0`。已撤销的墓碑可以再次导入。
5. 只打印站点、Profile、Cookie 数量和新修订，不打印任何名称或值。

退出码：0 成功；2 需要部署者操作（未登录、多账号、非法站点、未配置密钥、无可撤销会话）；3 宿主权限（TCC 或钥匙串拒绝）；4 数据库或并发冲突。钥匙串拒绝时，固定版本 yt-dlp 的解密器会对每行返回空值；读取器在“存在加密行但全部解密失败”时抛出权限错误，避免误报为未登录。

命令只读取 `.env`（或进程环境）中的 `DATABASE_URL` 与 `SITE_SESSION_ENCRYPTION_KEY`，只在宿主运行，这是唯一需要 macOS 钥匙串的地方。它替代 `provider_source_replica` 的登记与撤销。

### 6.2 容器初始化与恢复

`session-broker` 启动后每 15 s 扫描一次，把处于 `seeded` 的站点，以及 Profile 缺失的 `ready`／`degraded` 站点交给浏览器：

1. broker 经 `session_net` 调用浏览器 `bootstrap(site, seed_revision, jar)`。jar 以 broker→browser 会话的 X25519 临时密钥封装，浏览器进程内解密。
2. 浏览器为站点创建或复用 `/profiles/<site>/`，设置该 Profile 的代理为站点出口，通过 CDP `Network.setCookies` 写入，导航到 `keepalive_url`，执行 `login_probe`。
3. 结果和 `Network.getCookies`（仅限站点域集合）导出的 jar 回传 broker，由 broker 条件写入并推进状态。

Profile 卷存在时，重启后 Chromium 直接使用磁盘上的 Cookie，只需一次 `login_probe`。Profile 卷丢失时从数据库最新 jar 重建。两者都不需要宿主参与，满足 PRD NFR-01。

### 6.3 保活

浏览器对每个 `ready`／`degraded` 站点，每 30 min ± 5 min 随机抖动执行一次：导航到 `keepalive_url` → `login_probe` → 导出 jar。jar 与上次不同才回传，broker 以 `(seed_revision, jar_version)` 条件写入。浏览器同一时刻最多运行 2 个站点任务，每个站点任务 60 s 超时，超时即关闭该页面。

顶层导航用 CDP `Fetch` 拦截：只允许站点 Cookie 域和平台主机内的顶层导航，子资源放行。所有流量经 egress-proxy，私网目的地由既有 squid ACL 阻断。

### 6.4 执行（Runner 租约）

1. 下载 Worker／API 按 §3.4 选出 `site_session` 路线，把任务发给 `session-runner`（沿用 HMAC 调用），携带 `site`、冻结的 `seed_revision` 和任务 ID。
2. Runner 为本任务生成内存中的 X25519 临时密钥对，向 broker 请求 `lease(task_id, site, seed_revision, runner_public_key)`。
3. broker 检查状态为 `ready` 且 `seed_revision` 一致（不一致返回 `provider_session_not_ready`，由上层重新解析），用 X25519 + HKDF + ChaCha20-Poly1305 封装当前 jar。关联数据为 `task_id|site|seed_revision|expires_at`，有效期 10 min。封装实现复用现有 `provider_cookie_lease.seal_cookie_lease` 的算法，迁入 `app/workers/session/lease.py`。
4. Runner 解封后写入独占 tmpfs 的 `0600` jar，执行 yt-dlp，结束或取消时删除。跨副本单站点并发 1 沿用 Redis 凭据租约，键改为 `video:site-session-lease:{site}:{seed_revision}`。
5. yt-dlp 退出后，Runner 把 `--cookies` 回写的 jar 丢弃，不回传；Cookie 轮换只由浏览器负责，避免两个写者。执行得到认证类错误时，Runner 向 broker 报告 `(site, seed_revision, error_code)`。

访问上下文冻结 `site + seed_revision`，与 043 一致：保活刷新不使旧 inspection 失效，重新导入会使其失效。

**视频号**：`header_plugin=yuanbao` 的站点在第 2 步额外请求浏览器 `headers(task_id, site, runner_public_key)`。浏览器在该站点 Profile 中打开元宝页面，按现有 `yuanbao_session` 的读取逻辑生成动态头，同样用 Runner 公钥封装后返回。宿主专用元宝目录、LaunchAgent 和本机加密队列全部删除。

### 6.5 出口

`SITE_EGRESS_ROUTES`（JSON，`{"youtube.com":"http://…"}`，默认 `RUNNER_EGRESS_PROXY`）替代 `RUNNER_PROVIDER_EGRESS_PROXIES`。`egress_route` 在导入时写入记录；浏览器、Runner 和 bgutil（YouTube）都按记录中的路由选择出口。路由改变视为身份改变，需要重新导入。

## 7. 错误码与可观测性

| 变化 | 内容 |
| --- | --- |
| 新增 | `provider_session_not_ready`（503，可重试，`retry_after` 取 60 s） |
| 删除 | `provider_configuration_missing`（会话路线用途）、`provider_session_source_missing`、`provider_session_permission_denied`、`provider_session_unavailable`、`provider_session_not_allowed`，以及授权事务相关错误 |
| 保留 | `provider_auth_required`、`provider_session_expired`、`provider_verification_failed` 等内容与平台类语义；会话路线出现 `provider_session_expired` 时同时推动状态机 |

`/api/providers/status`（管理员）为每个站点返回：`site`、`provider_key`、`state`、`seed_revision`、`refreshed_at`、`verified_at`、`last_error_code`、`probe_strength`（`proven`／`retained`）和处理动作文本。不返回 Cookie 名、值或数量。

日志与指标按 `site`、`state`、`seed_revision` 分组；保活、租约、执行结果分别计数。

## 9. 安全分析

| 威胁 | 控制 |
| --- | --- |
| 浏览器被恶意页面利用 | 顶层导航限于已登记站点；无数据库、无密钥、无 RPC 访问内部业务；非 root、只读根、`cap_drop: ALL`；Chromium 随镜像固定版本升级 |
| Runner 被利用 | 只拿到当前任务单站点的 jar，10 min 过期，临时私钥只在内存；无法向 broker 申请其他站点（broker 按任务路由校验 `site`） |
| broker 被利用 | 不访问外网，不解析媒体；持有全部密文和密钥，是最高价值目标，只在 `session_net`／`runner_rpc_net` 上监听且需 HMAC |
| 导入读取过多 | 只读取站点域集合；打印计数不打印值；拒绝私网与公共后缀 |
| 会话被用于越权内容 | `entitlement=public_only` 的站点仍执行既有内容限制分类（private、会员、付费、DRM）并终止；账号会话不扩大权益 |
| 迟到写入复活撤销 | 条件写入 + `revoked` 墓碑，与 043 相同 |
