# 通用解析架构与实施计划

本文是所有 Provider 共用的目标设计、调研结论与实施顺序，针对“部分链接成功、部分失败、验证后仍失败、解析成功但下载失败”的服务级问题。当前实现与验收基线为 2026-10-01：P01/P02 的失败契约与持久执行、P03 的资源基础与宿主读取实现、P04 的自动状态与客户端契约、P05 的策略冻结传递已实施。服务重启后的哔哩哔哩首条任务和一条抖音公开内容已完成真实 Web 解析、下载、浏览器保存与完整解码，两者均为匿名路线；账号来源被本机 Keychain 拒绝，YouTube 尚未交付文件，账号冷启动和全平台验收仍开放。任务状态只在本文维护，[状态与待办](14-状态与待办.md)和 BACKLOG 只提供导航。

用户在完成方案调研后要求继续实现。当前按最小路径复用已有 Source、Broker、Runner 和 HTTP 下载，自动读取指定的日常 Chrome Profile，不增加人工平台接入或浏览器框架。第 5 节说明机制与停止条件，第 11 节记录实际实现和证据，第 12 节定义尚待完成的验收；已实现读取机制不等于本机已取得可用账号材料。

## 1. 使用场景与设计决策

帧取由部署者自行部署、自用，不计划上线为互联网服务。本轮以完整文件交付率、故障可解释性、原任务恢复和日常维护成本为目标，不建设多租户、隐私合规、商业解析 API、账号池、代理轮换或高可用集群。允许部署端持久保存浏览器原生 Profile 和平台登录状态；不为避免持久会话增加另一套分发系统。

选择以下架构：

1. 沿用现有 Provider Registry，声明每个平台的有序解析策略、所需上下文、失败后允许的下一步和验证器。
2. 主路径复用现有 yt-dlp 与下载流程，自动传入已有账号会话和必要请求环境。失败先区分来源读取、账号认证、平台依赖、提取器和媒体请求；平台适配器只负责已证实的上游差异，不拥有任务调度。
3. 当前 macOS 部署优先验证宿主按任务直接读取指定 Chrome Profile 的登录态，经既有来源接口交给 Runner。Browser Runtime 只补充有实际证据的页面依赖，不作为全部平台或首轮交付的前置。
4. 每次任务只有一个业务重试预算、一份持久解析计划和一个冻结的结果上下文；不并行竞速多个引擎，不在下载失败后静默换账号、客户端或出口。
5. 保留 PostgreSQL、Outbox、Temporal 解析工作流、RabbitMQ 下载和既有隔离媒体执行；不增加调度器、万能任务表或通用 Agent。

2026-09-30 用户进一步确认：解析与恢复必须自动完成，不要求人工接入、打开平台窗口、登录/验证后点继续。本轮不建设人工浏览器窗口、action/resume 按钮旅程或 noVNC。现有 Chrome 已登录的账号是批准来源，系统自动领取其会话；无法取得可用会话或平台没有可自动执行的已支持路径时，任务在既定预算内给出明确失败和诊断，不能以永久等待人工处理冒充自动恢复。此要求优先于本轮早期的人工恢复方案。

无感的产品目标为“粘贴链接 → 确认目标格式 → 获得完整文件”，中间不要求平台登录、导出 Cookie、点击扩展、启动来源或点继续。条件是部署端已有有效登录态、操作系统允许来源进程读取、目标内容和协议在支持范围内。已退出平台账号、尚未登录操作系统的全新机器与有效会话的服务冷启动是不同情况。

AGENTS、PROJECT、设计 08 和 README 已配套调整为固定 Chrome Profile 的宿主自动读取，允许官方提取器创建操作期临时快照，保持同一账号来源，不建立长期 Cookie 库。来源命令已清退扩展安装和平台登录入口；用户独立删除的扩展文件仍保留在工作区，不纳入此实现提交。

现有内容范围、非 DRM 要求、输入准入、取消和产物校验继续适用。浏览器策略解决请求环境与页面数据问题；平台协议不受支持或未提供可交付媒体时，返回明确能力缺口，不能把页面能播放视为文件已可下载。

| P01/P02/P04 已实现跨层失败、持久尝试和公开类型化投影 | 根因可表达，但来源和部分媒体网络证据仍缺实际验证 | 复用现有阶段与诊断，仅补实测所需信息 |
| P01 已为媒体命令标记 probe_media、transfer、validate，并保留最终失败的探测子因 | metadata 与媒体探测能够区分；重定向和出口诊断尚未完整保存 | P06 补齐按尝试持久化的媒体网络证据 |
| P04 已移除公开 login/resume 和人工等待入口，使用自动有界等待 | 来源实际不可用时，自动等待只能结束为失败 | 先闭合真实会话获取，再验收自动恢复 |

| 当前逻辑出口标识来自代理配置 | 不证明实际公网出口固定或与浏览器一致 | 明确绑定路由，并记录观测出口的时效与变化 |

抖音访客初始化与批准会话声明沿用既有实现。当前真实文件证据只覆盖第 11 节明确记录的匿名样本，账号路线尚未通过；不能将技术检查或公开样本成功扩展为所有内容修复。具体能力基线见[Provider](07-平台与Provider.md)、[会话来源](08-平台会话.md)与[工作流](15-工作流与平台下载目标.md)。

~~~mermaid
flowchart TD
  Client[Web / Flutter] --> API[持久意图与动作 API]
  API --> PG[(PostgreSQL：意图 / 计划 / 尝试 / 结果)]
  PG --> Outbox[现有 Outbox]
  Outbox --> WF[InspectionWorkflow：计时 / 恢复 / 取消]
  WF --> A[Activity：事务 claim 与单次执行]
  Registry[Provider Profile：策略与验证契约] --> Policy[共用选择规则]
  Policy --> A
  A --> Runner[现有 session-runner]
  Chrome[指定的已登录 Chrome Profile] --> Source[现有宿主 Source：自动按需读取]
  Source --> Broker[现有 Broker：转发操作租约]
  Broker --> Runner
  Runner --> HTTP[yt-dlp / 可信插件 / 经验证的适配器]
  Runner -.已证实的页面依赖.-> Browser[Browser Runtime：按需执行]
  Browser --> Preparation[自动访客初始化 / 批准会话领取]
  HTTP --> Egress[现有 egress-proxy]
  Browser --> Egress
  Runner --> Result[作品身份 / 格式 / 媒体探测]
  Result --> PG
  PG --> Download[既有下载 Job / RabbitMQ]
  Download --> Runner
  Runner --> Artifact[完整文件 / 校验 / 既有制品发布]
~~~

| 层次 | 所有权与约束 |
| --- | --- |
| Registry / Profile | 一份能力声明，包含策略顺序、来源选择、触发条件、协议和内容类型；不新增平行平台名单 |
| services/downloads | 纯规则根据持久能力快照、计划、失败证据、剩余预算与冷却选下一动作；不反向导入 workers，不发平台请求或读取浏览器文件 |
| repositories/downloads | 业务状态、计划、尝试、预算和 CAS 提交；状态与 Outbox 原子写入 |
| InspectionWorkflow | 唯一解析执行所有者；持久等待、定时和取消，重放不读取当前 Registry 或执行 I/O |
| Activity / integrations | 取得持久计划、claim 单次尝试、调用 Runner 并提交结果；稳定执行身份穿过进程边界 |
| session-runner | 一条策略的上下文准备、提取和探测；无递归业务回退、数据库访问或任务调度 |
| Browser Runtime | 浏览器进程、页面、Profile 互斥、自动上下文准备及当前执行资源；不保存任务账本 |
| RabbitMQ 下载链路 | 使用 inspection 的冻结上下文重新提取、下载和校验；保持当前 lease / heartbeat / DLQ |

首轮交付复用已有 Source、Broker、Runner，改变“如何从 Chrome 取得会话”，不移动整个下载进程到宿主，也不让容器挂载日常浏览器目录或操作系统钥匙串。容器没有宿主同用户的解密环境，直接在 Runner 添加 `--cookies-from-browser chrome` 不能自然解决该边界。已有 RPC、租约、临时文件和任务所有权继续使用。

Browser Runtime 已有资源基础；只有特定平台的 HTTP 路径经同环境对照仍缺页面能力时，才实现其固定页面逻辑。它不是登录态获取、普通 HTTP 下载、平台诊断或冷启动验收的共同前置；不因此新增容器或浏览器平台框架。

Runner 从现有 /internal/engine-catalog 返回 Registry 派生的策略能力与修订，integrations 将其校验为业务可用快照；计划创建后保存该快照，不在 services 另建一份平台声明。inspect/download 内部请求携带明确 strategy_id 和 plan_revision，Runner 对照本机 Registry 校验，拒绝未启用策略或版本不符；不会执行调用方任意传入的适配器、脚本或浏览器参数。

## 4. 有序策略与选择规则

ProviderProfile 扩展 resolution_strategies，使用固定类型、函数策略与组合，不引入 DSL。每条策略声明 strategy_id、adapter_id、adapter_revision、execution_kind、access_mode、session_source、context_requirements、allowed_failure_classes、media_handoff、validator、step_timeout_ms 和 enabled。启用前须有同策略完整文件证据；未经实现的条目保持禁用。

| 策略种类 | 适用情况 | 执行与结果 |
| --- | --- | --- |
| direct_http | 平台常规路径可直接取得可交付媒体 | 现有 yt-dlp 或可信平台插件 |
| prepared_http | 请求需要访客初始化、JS 或令牌，但不一定需要登录 | 同一策略内准备所需上下文；沿用 anonymous 访问模式，不恢复退休的独立 guest 路线 |
| session_http | 平台明确需要账号，或声明的批准路线需要会话 | 绑定部署者选定的一个来源与会话代；仍校验内容和媒体 |
| browser_page | 提取依赖真实页面、页面请求或浏览器上下文 | 自动准备匿名上下文或批准会话，执行固定页面逻辑，返回结构化作品数据与媒体交接能力 |
| alternate_adapter | 某平台已有经单独验证的第二种提取实现 | 与主适配器共享任务、来源和结果契约；只串行执行 |

规则固定：

- 首先选择 Profile 已启用的最轻量策略；公开账号平台默认匿名优先，个人权益平台沿既有明确账号路线。
- 准备访客上下文、生成令牌和读取批准的会话是不同需求。空 JSON、通用 403 或“需要 fresh cookies”不足以直接证明会话过期。
- 网络故障只允许同策略的有界重试；429 进入同一路由冷却；已知内容限制或删除直接终止；同一证据下不轮换策略试图解除平台限流。
- 提取器结构变化可走声明的页面适配或第二适配器；页面依赖、认证或具有已实现自动处理路径的验证可走对应浏览器能力。账号升级只在 Profile 许可且计划明确记录时发生；不向客户端派发人工动作。
- 策略不是一张必须全部跑完的清单。只执行证据允许的下一条；同一 strategy_id + context_key + evidence_signature 的无变化失败不再次自动调用。
- inspection 成功前可在同一计划中串行切换已声明策略；结果成功后固定最终策略。Profile、适配器或来源变化使旧结果要求重新解析。
- 没有可用下一步时保留具体根因；不落到未知站点 Generic、不调用公共解析站、不由 AI 生成执行脚本。

一个适配器内部可以有固定的页面/API 请求序列，但每步都记录阶段并受本次时限约束；该序列不改变访问方式、账号、客户端或 strategy_id。调用另一个策略、升级账号和业务重试只能由持久选择规则决定，避免把插件内部的请求序列变成隐藏的策略调度。

## 5. 登录态复用调研与最小实现方案

### 5.1 可选路径与推荐

调研日期为 2026-09-30。下表是机制比较，不是实际账号下载结果。

| 路径 | 复用已有账号 | 冷启动条件和限制 | 取舍 |
| --- | --- | --- | --- |
| 宿主 yt-dlp 浏览器 Cookie 提取 | 读取指定 Chrome Profile 已保存 Cookie | 同一 OS 用户、Profile 可读、系统解密权限可用；Chrome 关闭后不保证未落盘状态和会话 Cookie仍存在 | 当前 macOS 首选验证；接入已有 Source 接口，改动最少 |
| Chrome Cookies API + Native Messaging | 读取 Chrome 当前 Cookie Store | Chrome 必须在线且扩展已安装启用；扩展需自己实现 onDisconnect 重连，当前尚未闭合；首次安装仍有接入成本 | 比较候选；不作为本轮默认方案，不用失败后自动切换来掩盖读源错误 |
| CDP 操作日常默认 Chrome | 已允许运行调试的实例才可连接 | Chrome 136 起不接受默认数据目录的 remote-debugging-port/pipe；普通已运行实例也不能事后凭空取得 CDP | 不推荐作为现有登录态的默认接入 |
| 服务侧 Playwright 持久 Profile | 新 Profile 不自然继承日常账号 | 需先取得可移交状态或已有独立会话；复制跨 OS Profile 不等于复制解密环境 | 只有特定平台证明确需完整页面执行时再采用 |
| Playwright storageState 导入 | 取决于导出的状态是否有效 | 包含 Cookie/localStorage，IndexedDB 需显式包含，sessionStorage 不自动持久化；也不包含整个运行中的页面环境 | 页面路线的状态交接工具，非所有平台前置 |

yt-dlp [官方 FAQ](https://github.com/yt-dlp/yt-dlp/wiki/FAQ#how-do-i-pass-cookies-to-yt-dlp)直接支持浏览器 Cookie 提取与指定 Profile；项目锁定提交的 [cookies.py](https://github.com/yt-dlp/yt-dlp/blob/3a08beaf031ab68f966401ead017ac81fe8486cf/yt_dlp/cookies.py)已有系统解密适配，因此不自研 Cookie 解密器。当前没有证明本机钥匙串已授权该来源进程，首选路线必须先通过 5.5 节实验。

[Chrome 136 官方说明](https://developer.chrome.com/blog/remote-debugging-port)排除了默认 Profile 的通用 CDP 接入假设。[Playwright 认证状态说明](https://playwright.dev/python/docs/auth)和[持久上下文 API](https://playwright.dev/python/docs/api/class-browsertype#browser-type-launch-persistent-context)说明独立浏览器状态的能力；这些机制不能推导出“现有 Chrome 登录自动迁移成功”。

macOS 读取依赖同用户 Keychain 权限，首次可能触发 OS 授权；程序不能自行授予权限。Linux 还依赖钱包和桌面会话，Windows 新 Chrome 的 App-Bound Encryption 使直接读取不能作为跨 OS 承诺。这里是部署条件，不新增用户每次解析的授权旅程，也不承诺绕过操作系统限制。依据：[Apple 应用钥匙串权限](https://support.apple.com/en-gb/guide/mac-help/kychn002/26/mac/26)、[Chrome Cookie 加密机制](https://security.googleblog.com/2024/07/improving-security-of-chrome-cookies-on.html)。

项目锁定的 yt-dlp 原始 macOS 实现调用 `security find-generic-password`，并未提供禁用授权 UI 或读取超时的参数。外围超时本身不能保证不先弹窗口。本轮在隔离读取子进程中仅替换系统密钥查询：Security.framework 先禁止交互，再读取官方 `Chrome Safe Storage` / `Chrome` 项目；Cookie 提取和解密仍由固定版本 yt-dlp 执行。必须在实际 LaunchAgent/来源进程身份下验证无交互条件，不能以终端成功代替；出现系统授权窗口、人工点击后成功均不计为本轮无感通过。无法无交互读取时停止该实验，记录 OS 读取条件缺口，再评估来源选择，不扩大浏览器框架来回避结论。

### 5.2 主路径：替换会话获取，复用媒体链路

推荐先实施以下单一路径：

1. 在部署配置中固定一个已批准 Chrome Profile 和宿主用户，不按最近访问时间挑账号，不逐任务要求选择来源。
2. 任务按 Registry 的原有规则选择匿名或账号路线。固定公开路线继续匿名；已声明需要账号的路线自动读取同一 Profile。操作开始前读取当前可取得的已保存材料，不把一次导出的文件当成永久会话。
3. 宿主 Source 使用项目固定版本的官方提取能力，筛选本平台材料，返回已有 SourceSnapshot。读取有超时、并发和取消边界，结束清理官方临时快照；不新增 Cookie 数据库或后台保活扫描。
4. 保留现有 Source API → Broker → Runner 的操作租约。Runner 继续把 Cookie 用于本次 yt-dlp 解析、媒体探测和完整下载；既有密封机制无需为此重构。
5. 下载开工时重新取得同一作品的有效媒体地址，保留选定账号、必要头、客户端和出口，核对媒体 ID 与语义规格。相同 format id 或旧直链不足以恢复下载。
6. 完整文件通过身份、音轨、时长、大小、摘要、ffprobe 和完整解码后才发布；产品保存到设备的文件另做验收。

日常 Chrome 的 Cookie 会变化，特别是 YouTube 页面仍打开时。按需读取能减少旧快照问题，但读取成功仍须由实际平台请求证明接受；不得定期复制整个 Profile 或主动访问所有平台来“保活”。[YouTube Cookie 说明](https://github.com/yt-dlp/yt-dlp/wiki/Extractors#exporting-youtube-cookies)

锁定版本的官方实现复制主 Cookies 文件，不使用 SQLite backup，也未单独合并 WAL。若存在尚未 checkpoint 的写入或浏览器尚未刷盘，读取结果可能较旧；本次未检查真实 Profile，不能断言本机存在此问题。实验增加“Chrome 在线、正常会话更新后”的一致性检查，再决定官方读取是否足够，不先自研数据库快照。机制依据见锁定源码及 [SQLite WAL](https://sqlite.org/wal.html)。

会话版本只描述影响请求的材料和配置：绑定 Profile/账号来源、必要认证材料及行为修订。来源进程 PID、启动随机数、RPC 连接 ID、定时器不属于认证变化。相同材料经过 Source 重启应产生相同版本，冻结结果可以继续校验；账号、必要材料或客户端真正改变才走现有 context_changed/refresh。稳定摘要复用部署密钥，不额外保存一张版本账本。哪些 Cookie 属于身份和请求必需材料，由现有平台声明及实测确定，不能忽略真正影响授权的轮换。

版本稳定只允许继续校验旧结果，不证明旧 Runner 操作已结束。原操作仍按既有回执、fence 与 outcome_unknown 规则核对，不能利用来源重启重发不明结果的调用。Cookie 读取也不自动满足元宝等已有 HeaderPlugin 的页面身份/头契约，这类路径必须独立证明，不能交付缺少必要材料的“可用会话”。

完整执行上下文仍沿用现有结构：

沿用 ProviderAccessContext，补齐 strategy_id、adapter_revision、session_source_id、browser_context_revision、protocol_capabilities 和 egress_observation_ref；既有 Provider、Profile、access_mode、credential_version_id、client_profile_id、engine_commit、runtime_revision、attestation_provider_version 保留。Cookie、令牌和媒体直链不是业务 context_ref。

context_key 来自上述行为相关字段的规范化摘要。User-Agent、必要请求头、客户端参数、令牌类型/绑定条件、代理路线和浏览器版本均纳入 runtime_revision 或对应字段，不另建互相不一致的哈希。只有 adapter 能证明 HTTP 交接保持要求的上下文时，浏览器解析结果才能交给外部 HTTP 下载器。

解析和下载的网络环境不能只靠 Cookie 对齐。现有出口保持固定；适配器携带媒体所需头与客户端。代理配置摘要不等于观测公网 IP；没有观测时保持 unknown，不为首轮验证另建出口检测服务。对于明确绑定浏览器出口的失败，先比较实际环境，再决定固定的声明配置，不能换代理或账号试错。可交接要求的依据见 [yt-dlp 媒体环境说明](https://github.com/yt-dlp/yt-dlp/wiki/FAQ#i-extracted-a-video-url-but-it-does-not-play-on-another-machine--in-my-web-browser)。

### 5.3 冷启动的具体承诺

| 场景 | 必须证明的行为 |
| --- | --- |
| 服务重启，已有登录有效 | 第一条任务自行取得会话并完整下载；不需要人工启动来源或打开平台 |
| 来源重启，必要材料未变 | 来源自动恢复；相同认证版本保持稳定；解析后重启来源再确认下载仍正确 |
| Chrome 完全退出 | 验证已保存材料足够完成下载；未持久状态缺失是实际限制，不能用“可读数据库”替代结果 |
| 宿主重启且用户已登录 OS | 已有来源进程按用户启动机制恢复，首次任务无需启动脚本；Keychain 必须可用 |
| 临时直链或 Token 缓存为空 | 镜像内依赖已配套，任务自动取得本次所需数据；不依赖上一轮热缓存或启动后手工预热 |
| 运行中的 Worker/Runner 重启 | 遵循已有期限、预算、所有权和 fence；不能把来源恢复解释为可以重发结果不明的媒体调用 |
| 无账号、账号已注销、OS 用户未登录或解密权限拒绝 | 有界结束并报告具体前置条件缺失；不保证凭空完成首次登录或平台二次验证 |

当前承诺范围是这台 macOS 部署。迁往独立 Linux 服务器时，服务器没有桌面 Mac 的钥匙串；这是部署拓扑变化，需要另行选择来源，不能简单复制 Profile 就声称迁移完成。

### 5.4 平台差异保持薄层

通用流程只拥有任务、来源、期限、下载和校验；平台声明保留必要 Cookie、请求头、提取器参数及确有必要的页面逻辑。

| 平台/现象 | 先补齐的最少能力 | 明确暂不推导的能力 |
| --- | --- | --- |
| YouTube | 固定配套 yt-dlp/EJS/受支持 JS runtime；沿现有自动 PO Token provider 按请求提供材料；客户端支持所选会话和协议 | Cookie 不能替代 EJS/PO Token；一个 Token 不代表适用于所有视频或请求 |
| 抖音 | 先用最新会话和现有访客初始化验证提取器；detail API 空响应时，对照普通网页实际返回的数据与媒体请求 | fresh cookies 文本不证明登录过期；普通页面备选仍待真实完整文件，不承诺所有链接可用 |
| metadata 成功、媒体 403 | 核对 Cookie、必要头、客户端、Token 和出口；同环境取得新地址后再传输 | 不把通用 403 全部归为账号失效，不无限刷新来源 |
| 只依赖常规 HTTP 的平台 | 保留现有成功提取器和匿名路线，纳入冷启动回归 | 不为共享架构强制引入浏览器或账号 |
| 已证实需页面状态的平台 | 使用现有 Browser Runtime 执行一段固定逻辑，同一来源操作期注入状态，验证媒体可移交 | 不先建设 managed_browser 账号体系、全平台抓包、通用脚本或第二引擎池 |

[EJS 官方指南](https://github.com/yt-dlp/yt-dlp/wiki/EJS)要求脚本与提取器配套；[PO Token Guide](https://github.com/yt-dlp/yt-dlp/wiki/PO-Token-Guide)说明令牌请求类别和绑定条件。优先由成熟插件处理协议，项目不新建 Token 管理服务。调研时上游 bgutil 最新发布为 2.0.0，项目仍固定 1.3.2；选版本时须成对验证插件和服务端的接口、地址与启动方式，不能只升级其中一端。

当前 master 的客户端默认值和 Wiki 表格可能不同步，不能直接应用到项目锁定提交。实施以固定版本源码、配套配置和实际媒体结果为准；升级作为一个可回滚的独立验证步骤，不设置 player_client=all 来碰运气。

抖音上游 [DouyinIE 源码](https://github.com/yt-dlp/yt-dlp/blob/master/yt_dlp/extractor/tiktok.py)、[问题 #9667](https://github.com/yt-dlp/yt-dlp/issues/9667)及[报告 #16867](https://github.com/yt-dlp/yt-dlp/issues/16867)说明 Cookie 之外仍可能有提取缺口。issue 是特定环境报告，不能作为本项目失败原因的确定证据。页面路线只处理已允许的正常页面和清晰媒体，不增加验证码求解、DRM 转换或权益扩张。

### 5.5 最先验证的假设与止损条件

以下是最小来源的验证假设。当前实际非交互读取已被本机 Keychain 拒绝，匿名完整文件不能替代账号实验；其余未完成项保留为后续门槛，执行事实见第 11 节：

| 假设 | 最小实验 | 通过/停止条件 |
| --- | --- | --- |
| 官方读取适合本机无感运行 | 固定现有 Profile，由实际 LaunchAgent/来源身份按任务读取目标站点；另测拒绝/锁定 | 无系统授权窗口，有限时间返回；拒绝/超时准确失败，子进程确认结束；出现人工授权则本项不通过 |
| 在线读取不会错用旧状态 | Chrome 保持在线，正常会话更新后重新读取并验证平台请求 | 材料被平台接受；只复制文件成功不算；若一致性不足先定位，不扩大通用框架 |
| 材料被平台接受 | 对当前失败的 YouTube/抖音样本，在同一环境用现有提取器执行 | 取得匹配输入的作品身份与可传输媒体；仅有 Cookie 名称不算通过；失败定位到来源、平台依赖、结构或媒体阶段 |
| Chrome 不在线仍可用 | 完全退出 Chrome 后，执行同一支持样本 | 不借助已缓存直链/Token完成完整文件；否则缩小该承诺并明确缺失材料 |
| 来源重启不冒充认证变化 | 比较必要材料不变时的版本，并执行“解析→来源重启→确认下载” | 版本稳定、内容一致、无重复 Job；材料真的变化仍拒绝旧结果 |
| 最小方案可以覆盖产品目标 | YouTube、抖音各两条，既有哔哩哔哩基线及一个明确依赖会话的已支持样本；记录实际 access_mode | Web 仅输入/确认即可完整保存，首次、重复、重启均有文件证据；账号样本证明会话确被使用，匿名成功不能代替；未通过先解决已知阶段 |

只有上述实验明确证明 Cookie + HTTP 提取不足，才进入对应页面策略或第二适配器对照。全 Registry 状态仍需诚实记录；首轮小样本成功不代表全平台稳定。

公开匿名样本无需新增账号 whoami 探测。对于明确依赖会话的样本，由实际媒体请求被接受证明本次任务可以使用该会话，不额外建设账号校验服务。

## 6. 全阶段失败契约

统一失败事实包含 code、phase、scope、evidence_kind、strategy_id、context_key、retry_after、observed_at 和 diagnostic_ref。phase 固定为 recognize、prepare_context、fetch_metadata、select_format、probe_media、transfer、validate、publish；scope 固定为 content、session、route、dependency、runtime。失败动作由共用规则决定，平台 stderr 仅作为证据输入，不能直接控制 UI 或任务状态。

| 失败类别 | 必要证据或语义 | 下一步 |
| --- | --- | --- |
| auth_required / session_expired | 明确登录要求或明确认证材料失效；不能仅依赖缺字段 | 自动领取/刷新同一批准来源，或已声明会话路径；没有有效会话则保留认证失败 |
| challenge_required | 平台返回可识别的验证页面/响应 | 已声明且实现的自动 browser_page 路径；没有自动处理能力则保留验证失败 |
| token_unavailable / token_rejected | 指定令牌 Provider 不可用或令牌请求被拒绝 | 受影响依赖冷却/修复；只允许同绑定的已验证令牌替代 |
| extractor_changed | 预期结构不匹配且没有明确内容限制 | 已声明页面/第二适配器；否则适配器退化 |
| protocol_unavailable / format_unavailable | 有作品信息但缺少当前引擎可交付的协议或规格 | 已声明协议能力/适配器；用户重新确认规格 |
| media_probe_failed | metadata 已成功，媒体探测没有通过 | 保留实际子因，如连接、重定向、格式或媒体限制；不改写登录 |
| egress_denied / network_transient | 代理拒绝、DNS/TLS/连接超时等明确网络证据 | 网络诊断或同策略退避，不升级账号 |
| rate_limited | 明确 429 / Retry-After 或已确认平台限流 | 共享路由冷却；预算允许时原任务等待 |
| content_unavailable / content_restricted | 删除、访问限制、DRM、试看或权益不符 | 明确终止或现有文件导入入口 |
| context_changed | 结果上下文与执行上下文不符 | refresh；旧格式重新确认 |
| runtime_unavailable / capacity_exhausted | Runner/浏览器未就绪、Profile 忙、进程启动失败或本机资源不足 | 运行诊断或有界资源等待，不提示重新登录，不切平台策略掩盖服务故障 |
| invalid_input / source_unsupported | 输入不合法、无法识别或不在已声明范围 | 明确输入/能力错误，不启动账号来源或重试平台 |
| artifact_invalid / storage_unavailable | 文件校验失败、磁盘不足或对象存储发布失败 | 按 validate/publish 阶段处理；有效产物发布重试不重新解析下载 |
| outcome_unknown | 无法确定旧执行是否结束或是否已提交结果 | 先核对所有权/产物；未确认停止前不重发 |
| upstream_unclassified | 只有模糊提示、空响应等不足以确认根因 | 保存已知阶段和证据；允许已声明的同访问范围诊断路径，否则明确失败 |

同一次执行先判断明确内容限制或删除，再判断具体令牌依赖证据、最终限流响应、明确认证/挑战、网络证据、结构/能力不足与未分类提示。指定令牌 Provider 的本地不可用证据不能改写成登录；最终 ERROR 中的 429 优先于模糊登录提示，较早 WARNING 中的 429 不覆盖明确认证或内容限制。YouTube 笼统的 video unavailable 提示不能覆盖同次执行观测到的 429。空 JSON 或通用媒体 403 本身不证明账号失效或验证码。

业务层、Canary、任务历史和客户端须保留根因；面向产品的摘要码可以与原始 failure.code 分开表达。多次策略失败保留各自证据，最终摘要指出停止原因，不仅展示最后一条 stderr。失败事实另含 failure_class 和可选 cause_code，分别支持共用规则和具体子因；不携带原始 stderr 或任意 URL。

## 7. 持久计划、尝试与唯一预算

沿现有 download_intents 增加不可变 resolution_plan、next_strategy_id 及最终选择引用。计划在首次平台 I/O 前提交，包含 Profile 修订、内容类型、策略候选与触发条件、来源选择、总预算和 plan_revision；下一条选择属于可 CAS 更新的业务投影，不改写计划头。Workflow 只传 intent_id、generation 等引用，不能在重放时重新读取可变 Registry 决定过去的选择。

增加必要的 resolution_attempts 子记录，属于 downloads 域，不是新任务系统：

| 字段/约束 | 目的 |
| --- | --- |
| intent_id、generation、attempt_no；三者唯一 | 关联原任务和最多 3 次实际解析调用 |
| operation_id 唯一、fence、strategy_id、plan_revision、context_key | operation_id 由 intent/generation/attempt_no 稳定派生；平台 I/O 前登记，SDK 重试不另造执行身份 |
| started_at、finished_at、duration_ms、status | started / succeeded / failed / abandoned / outcome_unknown；状态更新幂等 |
| failure_code、failure_phase、failure_scope、evidence_kind、diagnostic_ref | 保留业务决策必需的失败事实，不复制 Temporal History |
| inspection_id 或最终结果引用 | 明确被业务库接受的结果；不由 workspace 文件决定成功 |

结构仅在 backend/sql/schema.sql、ORM、Repository 与测试中维护；对既有数据库幂等应用，空库使用现有 PostgreSQL 服务的隔离测试库。删除意图按现有生命周期清理子记录，Provider 能力证据独立保存。

预算目标沿用每 generation 180 秒有效执行时间、最多 3 次实际策略调用。direct_http、上下文准备路径、浏览器路径、备用适配器、网络重试和恢复后的调用共同消费该预算；内部请求与探测共享本次剩余时间。策略执行前的来源检查失败可以等待；实际策略调用一经登记并提交执行就不退回计数。仅用户明确 refresh/重新运行才开启新 generation，自动恢复不重置次数或剩余时间。

执行前的资源预检查与策略调用分开：Profile 忙、来源未连接或 Worker 槽位不足可在尚未提交策略时有界等待，不消费策略调用次数，但受已有排队期限和剩余时间约束。策略已提交后才发生的动态资源失败仍消费本次额度，不能按错误文本退回预算或无限重启执行器。Profile 互斥等待不能伪装成 session_expired，Runner 拒绝/本机资源故障不能计为上游平台验证失败。

每次 Activity 只负责一条策略。仓储先登记尝试并扣额度；结束时原子记录耗时、失败和下一条选择。可立即继续的备用路径回到 queued，由现有 Workflow 下一轮执行，不能再产生一个启动 Workflow 的 Outbox 命令。临时故障与可自动准备的上下文进入 retry_wait，由 Workflow 定时器等待；没有自动恢复路径则失败。状态变化同步更新现有 operation_id 与约束。

平台执行 Activity 的 SDK maximum_attempts 设为 1，下一次合法策略调用由 Workflow 根据持久事实驱动；失联时先按稳定 operation_id 核对结果和旧持有者，不能确认旧操作停止则 outcome_unknown。数据库结果提交可以重试同一幂等提交。Runner、HTTP 客户端和平台插件不额外增加整请求业务重试；下载器的必要分片重试计入下载总预算。

自动恢复只有实际会话/页面状态变化或明确修复证据才能更新上下文与去重条件；定时器、刷新页面或重启本身不能制造新 context_key 绕过无变化失败限制。等待不延长排队截止，不重置已消耗预算。P04 删除人工等待身份与 24 小时人工等待状态，并对更新前未结束的任务明确收敛，不能让它们卡在已经删除的客户端入口。

## 8. 解析结果、下载与完整交付

ready 必须同时满足作品身份明确、访问结论允许、存在至少一项可执行语义下载计划、必要媒体探测通过。metadata_ready 只作为阶段诊断，不另建可确认下载的成功状态。

最终 inspection 固定内容身份、媒体类别、strategy_id、adapter_revision、context_ref、协议能力、完整时长/资产预期与格式选择。后续下载只按这份策略和上下文重新提取短期地址；不会从 browser_page 成功后退回另一个未经验证的默认提取器。

浏览器结果的媒体交接分为：

- http_transferable：适配器证明必要的 Cookie、头、客户端与出口能在已声明 HTTP 路径中表达，Runner 取得新直链后进行完整下载与校验。
- browser_transferable：平台确实提供受支持的普通下载或可交付媒体路径，由同浏览器上下文下载到既有 workspace；文件保存完成后才关闭上下文，再经公共校验和发布。此能力逐平台启用，不从播放页面推断。
- unsupported：只能获得页面播放信息、缺协议下载支持或无法证明完整媒体交接；该策略不能产生 downloadable inspection。

更换策略、来源或账号意味着重新解析和重新确认格式；下载链路可返回关联原意图的 refresh 动作，但不会自动建立另一套解析工作流。发布失败只恢复已有产物，不重新登录和下载；AI 失败不改变下载成功。

文件验证复用 ffprobe、完整 FFmpeg 解码、SHA-256 和既有资产模型，核对时长、音视频流与作品身份；图集逐项核对数量和清单，不伪造视频格式。已接受的产物引用可用于幂等恢复，未登记文件保持待核对或孤儿状态。

平台状态分别投影 configured、context_readable、metadata_checked、media_verified、degraded 或 unsupported 的事实；这些为展示维度，不强行替换现有业务状态枚举。平台下载能力与 AI/报告证据分开。按引擎、策略、访问方式、出口与时间窗口记录通过数/总数，不把一个成功链接覆盖整个平台失败。
