# 下载故障修复与持续可用性 SOP

## 1. 适用范围与当前状态

本 SOP 用于帧取的“项目重启后无法下载”“解析时反复要求登录”“单个平台间歇失效”等问题，从接报、定位、设计、实现一直执行到部署、回滚和真实交付验收。

**状态：公共出口、登录误分类、部署拓扑和 Web 下载页面刷新已分项修复；来源独立与换机仍未通过。** 详细设计见 [035 设计](../design/035-平台访问与会话恢复能力设计.md)。执行本 SOP 时必须重新采集运行状态，不能把历史记录当实时状态。

本 SOP 是执行入口，长期技术决策与架构规范继续维护在既有设计文档中：

| 资料 | 唯一职责 |
| --- | --- |
| [Server AGENTS.md](../../AGENTS.md)、[App AGENTS.md](../../../video-app/AGENTS.md) | 仓库边界、开发、验证、提交规则 |
| [035 Design](../design/035-平台访问与会话恢复能力设计.md) | 策略、来源所有权、修订与恢复设计 |
| [030 设计](../design/030-运行故障隔离与恢复设计.md)、[031 设计](../design/031-Linux无人值守运行设计.md) | 进程隔离、排空、重启与文件来源恢复 |

初期共同出口、部署输入和误分类已有分项交付，不重复执行已关闭缺陷。后续按 **S0 来源诊断 → S1 无日常 Chrome 恢复基线 → S2 平台增量实验 → S3 单来源维护 → S4 真正换机 → S5 持续适配** 推进；未通过候选不得加入默认路线。历史调研与方案演进通过 Git 追溯。

先判断用户是换客户端访问同一服务，还是迁移整个服务。前者不搬平台来源，后者按规范恢复业务数据、制品、配置、密钥与来源，防止旧备份复活撤销授权。站点会话的换机只需恢复 PostgreSQL 并沿用 `SITE_SESSION_ENCRYPTION_KEY`，见 [011 手册](011-站点会话运行手册.md)。

## 2. 执行规则

1. `Video/` 是父目录；`video-server` 和 `video-app` 分别检查、修改、验证与交付。开始前保留已有未提交改动，不清理用户工作树。
2. 先对齐 Design → PRD → Plan → Acceptance，再执行本切片的 Red → Green → Refactor。既有文档已定义的内容直接复用，不复制一套新设计。
3. PostgreSQL 是任务状态事实来源；复用已有数据库、RabbitMQ、Redis/Valkey、MinIO。不能为本机验证启动 CI 基础设施夹具，也不能用清库恢复服务。
4. 只有 schema 确实变化才更新并应用 `backend/sql/schema.sql`；同时验证空库和已有当前态库，使用现有服务中的隔离测试空间。纯 Compose 或错误分类修复不执行数据库结构变更。
5. Provider 来源与 FrameFetch 登录分开。普通业务请求、App、日志、截图、Git 均不接收原始 Cookie/Token；只读取已授权平台来源。
6. 保留匿名/受控 Runner 隔离、出口 ACL、下载前重解析、严格 context、Outbox、任务幂等与制品验证。不通过换账号、放开私网或忽略媒体失败来获得绿色结果。
7. 已有用户授权继续有效，不机械重复询问。实施过程中新增目标机器、账号、破坏性操作或超出现有范围的发布动作，按当时授权范围处理；本 SOP 本身不表示这些动作已经执行。
8. 每个可独立说明和回滚的小切片单独交付。Server 按 AGENTS 完成后本地提交；App 仅在用户明确要求提交时提交。推送、分支、PR 与外部发布按各仓库授权规则执行。

## 4. S00：接报、保护现场与确定入口

### 操作

1. 记录发生在哪个页面/客户端、哪一个平台、具体动作、可见错误和时间。用户原始链接私下保留，公共记录使用样本 ID；确认是 FrameFetch 登录页跳转，还是平台授权提示。
2. 标明触发方式：普通进程 restart、Compose 重建、Docker Desktop 重启、整机重启、部署升级或无重启。未知时先记未知，不自行归因为 Cookie 过期。
3. 分别记录两个仓库状态。以下命令从 `Video/` 执行：

```bash
git -C video-server status --short --branch
git -C video-server rev-parse HEAD
git -C video-app status --short --branch
git -C video-app rev-parse HEAD
docker ps --format '{{.Names}}\t{{.Image}}\t{{.Status}}'
```

4. 从当前容器标签和已有运维配置核对真正生效的 Compose 文件，而不是凭 `.env.prod` 文件名猜测。用定向字段读取，不输出完整 `docker inspect` 的 Env：

```bash
docker inspect --format '{{index .Config.Labels "com.docker.compose.project.config_files"}}' video-api
docker inspect --format '{{.Image}}' video-api
docker inspect --format '{{.Image}}' egress-proxy
docker inspect --format '{{.State.Status}} {{.State.ExitCode}} {{.RestartCount}}' egress-proxy
```

5. 记录活动下载、待处理任务和正在登录/导出的会话。尚不清空队列、重启 Worker、关闭用户登录窗口或重建全栈。

### 通过与失败处理

通过：目标仓库、运行入口、影响层级和已有改动已经记录。若缺少用户原链接，可继续共同基础设施诊断；最终原链接验收保持待补。不得把前次研究中的 795 次重启或四个平台来源探测结果写成本次新证据。

## 5. S01：按层诊断，先排除共同故障

按下表从上到下检查，避免对每个平台重复刷新账号。

| 层级 | 操作 | 判定与下一动作 |
| --- | --- | --- |
| 核心 API | 访问 `/health/ready`，核对核心依赖 | 核心不可用先诊断 DB/MQ/Redis/MinIO/schema；不能直接改 Provider |
| 公共出口 | 代理状态、退出码、定向日志、Runner 到代理的 TCP/协议探测 | 多平台共同失败且出口不可达，优先 CQ-029/部署；保留来源 |
| Runner | 容器、DNS、端口、二进制、workspace、readiness | 缺实例/旧镜像/权限错误归运行配置，不归登录 |
| 会话来源 | 文件存在/权限或无 Cookie 的代理 probe；记录 source kind | 来源通道可用不等于账号有效；离线/锁定/超时不注销账号 |
| 平台解析 | 固定来源和上下文的小样本 metadata；保留阶段错误 | 明确区分空响应、429、挑战、权限、页面结构变化 |
| 媒体与制品 | 下载、ffprobe、完整解码、MinIO 长度/哈希 | 解析成功但媒体失败，定位 CDN/音轨/传输/校验 |
| 客户端 | 实际文件保存、播放、站内登录状态 | 后台成功不覆盖 Chrome 策略、手机 HTTPS 和设备保存失败 |

核心 API 与代理只读检查：

```bash
curl --fail --silent --show-error --max-time 5 http://127.0.0.1:8111/health/ready
docker logs --tail 50 egress-proxy
```

日志在本地检查，写入文档前脱敏。涉及平台/业务容器的日志不能直接整段复制；不要输出 Cookie、带签名的媒体地址、完整请求头或 token。

**诊断决策：**

- 看到残留 `/tmp/squid.pid`、PID 1、`egress-proxy` 连续退出或端口策略异常，进入 S03；不要要求所有平台重新登录。
- 端点缺失、来源方式与部署不符、引用临时文件，进入 S04。
- 已带来源仍因 Fresh cookies/空 JSON 提示登录，进入 S05-A。
- 来源明确不存在/失效才按来源类型恢复；涉及账号变更、修订不明，进入 S05-C。
- 出口正常、来源正常、某平台媒体失败，进入平台专项；保存首轮失败结果。

## 7. S03：共同出口最小修复

### Red：稳定复现

1. 用当前已存在的 Squid 镜像 ID 创建临时容器，`network none`、不发布端口、不接业务网络或凭据；只操作本次创建的容器及自动卷。
2. 保留当前前台启动和 PID 文件路径，验证首次启动成功。
3. 对临时容器执行强制终止后同容器 start，记录原配置退出码及残留 PID 错误。正常 stop/start 单独记录，不能替代强杀场景。
4. 复现结束清理本次临时资源，不执行 Docker 全局 prune。

### Green：候选实现

同时修改两个业务 Compose 文件中 `egress-proxy`：

```yaml
tmpfs:
  - /tmp:rw,noexec,nosuid,size=16m,mode=1777
```

保持固定 Squid 镜像、`pid_filename /tmp/squid.pid`、PID 健康检查、受控网络和目标 ACL。不要仅删除一次 PID 文件，也不要把 PID 禁用后保留已失效的 `squid -k check`。

### 验证与转出

- 原配置失败、候选成功的对照成立。
- 使用完整实际 Squid 配置验证权限、启动、转发及私网目标拒绝；最小 `deny all` 实验不代替此项。
- 正常停止恢复和强杀恢复分别至少 3 轮，保持同一候选镜像、配置与测试身份。
- 两个业务 Compose 均通过静态解析；停止宽限仍覆盖既有预算。

完成后以本切片走 S06/S07/S08；真实媒体验收之前 CQ-029 保持“已修复待验收”。如果原镜像无法复现，先重新核对日志、PID 路径和启动参数，不能直接修改无关登录代码。

## 8. S04：部署固化、预检和恢复配置

### 8.1 固化最终输入

1. 列出现行 Compose 文件、profiles、默认策略、Operator 实例和对应来源方式。
2. 对照当前容器镜像 ID，重建缺失临时覆盖所表达的最终配置，写到持久部署配置中。不能凭当前可变 `prod` tag 推断历史镜像，也不能随手删掉覆盖层。
3. 记录无 Secret 的发布清单：代码 commit、镜像摘要、引擎/插件/JS/FFmpeg/PO Provider 版本、宿主来源代理代码版本、配置文件清单。
4. `.env.prod`、平台来源和敏感配置继续私有存放；不把展开全部变量的 Compose 配置提交 Git。

### 8.2 固定本次命令入口

以下示例从 `video-server/`、zsh 执行，适用于当前单文件生产拓扑。来源方式由 `docker-compose-prod.yml` 内各平台 Runner 固定；不要临时增加覆盖文件改变来源。

```bash
FF_COMPOSE=(docker compose --env-file .env.prod -f docker-compose-prod.yml)
"${FF_COMPOSE[@]}" config --quiet
"${FF_COMPOSE[@]}" config --services
"${FF_COMPOSE[@]}" ps
```

`FF_COMPOSE` 只是本次 shell 的明确命令参数，不是新部署服务。`.env.prod` 同样固定 `COMPOSE_FILE=docker-compose-prod.yml`，显式参数和日常入口必须解析为同一拓扑。

### 8.3 预检清单

- 每个默认/允许受控策略都有对应 Runner 和正确 source kind；缺失项选择恢复已声明路线，或明确移出允许集合，不能静默换匿名/账号。
- 平台文件挂载与权限正确；动态来源用无 Cookie probe；不批量导出全部浏览器凭据。
- 镜像摘要与发布清单一致；不混用旧 Worker、新 Runner 和不兼容 RPC。
- workspace、依赖、必要 schema 完整；基础设施直接复用。
- 正式宣称启用的 Canary 有真实目标；空列表显示“监测未配置”。

未来如补自动预检 CLI，复用现有 Python 工具入口，并先写对应测试。本 SOP 不提供一个尚未实现的 `doctor` 命令冒充现有能力。当前可用定向 Docker 检查、管理员运行诊断和既有健康接口完成清单。

## 9. S05：分类、依赖、会话和平台专项

### S05-A：修复登录误分类

**修改位置：** `provider_errors.py`、`integrations/media_runner.py`、相应测试；只有用户动作/文案发生变化才调整 Web/App 对应映射。

先增加或修改这些反例：

| 输入/场景 | 必须断言 |
| --- | --- |
| 已认证 + 空 JSON + Fresh cookies | 不直接宣判未登录；无明确原因时保留临时失败 |
| 未认证 + 同样模糊错误 | 不能只凭字符串要求账号登录，访客验证与账号区分 |
| 明确没有来源 | 来源缺失准确提示，不自动寻找其他账号 |
| 明确过期/撤销 | 准确失效，旧 context 不继续执行 |
| 429 与混合登录提示 | 优先明确限流，遵守冷却，不循环刷新账号 |
| 来源锁定/代理断连 | 运行暂不可用，保留已有授权 |
| 挑战页/验证码 | 平台验证失败，不自动反复尝试 |
| 平台 422/429/503 | FrameFetch 登录保持；不跳转站内登录页 |

实现遵循证据优先并复用既有稳定错误码，旧测试中不正确的期望同步修正。额外重试必须共享绝对 deadline、同一 context 和总预算，避免 Worker/HTTP/yt-dlp/plugin 多层重试放大；冷却不得因重启、换 Cookie 或删除任务清空。

### S05-B：bgutil 配套依赖升级

按 021 的来源记录复核目标版本和发布变化，在候选环境成对更新插件、Provider 与项目 supervisor 的版本约束。保持专用网络，验证默认监听变化不会阻断 Runner，确认错误响应仍按正确原因分类。

验证顺序为：依赖/监听契约 → 原网络可达 → token 获取 → 同样本 metadata/media → Provider 重启后重测。本机未发布宿主端口的事实不能替代依赖修复，也不能直接套用默认公开监听部署的受影响结论。此项独立提交，不混入代理 tmpfs 修复。

### S05-C：会话来源修订与复用

已由 [046 容器自持平台会话](../plan/046-容器自持平台会话Plan.md) 取代：会话修订（`seed_revision`／`jar_version`）、单写者条件写入、撤销墓碑、单任务租约与“重新导入使旧 context 失效”均在 046 中实现并验收。

### S05-D：平台专项

保持 021 的 23 平台矩阵；视频号间歇失败、Vimeo 音轨、红果 ffprobe 5xx、优酷/腾讯完整个人下载分别对应已有 CQ/专项。每项固定样本、策略、引擎和出口，先复现再修复。

每一场景都记录前后任务状态、来源修订、恢复耗时和完整文件结果；会话仍有效的前提下，交互登录次数应为 0。

## 12. 失败处理与回滚

| 失败位置 | 立即动作 | 后续条件 |
| --- | --- | --- |
| Red 未复现 | 停止扩大修改，核对真实执行对象与版本 | 有稳定反例或明确证据再修 |
| 单测/契约/配置失败 | 留在候选阶段修复 | 不部署、不删除检查 |
| 候选真实样本失败 | 保留原错误与第一轮结果，判断内容/来源/网络 | 不通过换账号或降低校验放行 |
| 部署后新增核心回归 | 停止推广候选，回退受影响服务的已验证镜像/配置 | 回退后重新验证核心和原路线 |
| 来源失效/撤销 | 停发旧 epoch；一次准确通知来源所有者 | 显式恢复授权后重新解析，不恢复已撤销备份 |
| 单平台上游变化 | 降级对应能力，保留其他能力 | 该平台候选修复通过后再恢复 |
| 服务端成功、设备保存失败 | 保留制品，定位客户端/网络/浏览器策略 | 实际文件保存验证；不重复抓取平台掩盖 |

回滚步骤：

1. 记录失败版本、任务与证据；停止该候选继续接收受影响工作，保留任务和消息事实。
2. 从发布清单取出上一个已验证镜像与完整持久配置；确认文件/镜像存在。
3. 排空后重建受影响服务；回滚镜像若与当前 schema/RPC 不兼容，先制定安全前向修复，不能盲目降级。
4. 不清库、不 `down -v`、不删除冷却、不改写任务成功、不恢复已撤销凭据。全栈清理不属于本 SOP 的恢复手段。
5. 重新执行核心健康、受影响路线和文件交付验证，在 Acceptance 中记录回滚结果。

Generic 长尾线路发布后，待处理或在途的 `generic` 意图／下载任务要求支持 Generic 按 key 上下文与单媒体归属校验的 Runner。更早镜像会将其误判为不可重试的平台不支持；只有确认该类任务已排空，且维护窗口内已停止新接单，才能向更早镜像降级。当前没有单平台维护开关，不能以为仅暂停某个 Worker 就阻止了新意图。保留首个支持该契约的镜像作为后续最低回滚版本；无法满足排空条件时采用安全的前向修复，不直接降级。

对于出口代理故障，回到旧版本不等于恢复完成。应保留准确的不可用状态，修正候选
权限、版本或策略并再次验证，不能用单次 TCP 健康检查替代真实代理策略验收。
